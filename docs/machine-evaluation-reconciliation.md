# 機種別評価と議事録の照合メモ

最終更新: 2026-06-07

## 目的

機種別評価の実装結果が、ChatGPT議事録のバックテスト結果とずれる場合に、原因を順番に切り分けるためのメモです。

ネオアイムの修正で分かったことを、他機種の修正にも使える形で残します。

## ネオアイムで起きていたこと

議事録の本命条件は、おおむね次の結果でした。

- 132件
- 938,469G
- RB 1/271.3
- 合成 1/130.7
- 差枚 +157,837
- 機械割 105.61%

Webアプリ上では件数や内容がずれていたため、アプリを使わずに、議事録へ渡したCSVを直接使って単体バックテストを行いました。

その結果、主な原因は次の2つでした。

- 点数計算に、ネオアイム用の弱内容日が入っていなかった
- 採用条件が、議事録の本命に対して広すぎた

修正後の採用条件は次です。

- 1位
- 機種別点数70点以上
- 3日差枚-1,700以下の沈み滞在2日以上

弱内容日は次の定義で点数へ加味します。

- G数3,000以上
- 合成1/170以上
- RB1/400以上

修正後のWebアプリ結果は次の水準まで寄りました。

- 128件
- 912,565G
- RB 1/271.4
- 合成 1/130.6
- 差枚 +155,810
- 機械割 105.7%

件数は4件少ないものの、RB、合成、差枚、機械割の質がかなり近いため、この状態をネオアイムは合格扱いにします。

## 今回の気付き

議事録とのズレは、点数の境界を無理やり動かして合わせるのではなく、まず定義の違いを探す必要があります。

特に重要だったのは次です。

- 「70点以上」は、共通狙い度ではなく機種別点数の70点以上として扱う
- 「1位」も、共通狙い度順位ではなく機種別点数の順位として扱う
- 採用条件と点数計算は別物として確認する
- 「弱内容」「高内容」「処遇完了」「沈み滞在」などの言葉は、議事録内の実際の定義まで戻って確認する
- 件数だけを合わせると危険で、RB、合成、G数、差枚、機械割も同時に見る
- 期間の端、履歴不足日、同点順位、欠損データで数件の差は起きうる
- メインロジックを変えて結果が変わる機種は、推定設定などの列を間接的に使っている可能性がある
- Aパーク春日店では、特定日や曜日による直接加点は入れない

## ミスタージャグラーで起きていたこと

ミスタージャグラーは、期間を議事録の実績対象日に合わせるため、Webアプリ上では予測日ベースで 2025-07-03 から 2026-06-01 を指定する必要があります。これは翌営業日の実績として 2025-07-04 から 2026-06-02 を集計するためです。

期間を合わせた後のWebアプリ結果は次でした。

- 101件
- 657,380G
- RB 1/293.1
- 合成 1/134.2
- 差枚 +87,244
- 機械割 104.4%

議事録の推奨条件は次です。

- 1位
- 60点以上
- 次点差10点以上

議事録の結果は次でした。

- 94件
- 617,894G
- RB 1/288.6
- 合成 1/133.0
- 差枚 +87,677
- 機械割 104.73%

独自集計で確認したところ、現行実装の1位・60点以上・次点差10点以上は101件でWebアプリと一致しました。次点差を14点以上にすると94件へ近づきますが、これは議事録本文にない条件変更のため採用しません。

実装側で直すべき差は、点数表のE枠とF枠でした。

- E: 返済未完了・周辺取り残されは最大10点
- F: 前日ボーナス内容の本物感は最大6点

以前の実装では、この2枠を合算して最大16点としていたため、返済未完了側だけで点数が乗りやすくなっていました。修正後は議事録の点数表どおり、返済未完了を最大10点、前日内容を最大6点として別々に丸めます。

この修正は94件ぴったりへ合わせるためではなく、議事録の点数表に実装構造を合わせるための修正です。

## モンキーVで起きていたこと

モンキーVは、最新議事録で「台番変更前後を並び順でつなげず、台番変更時に履歴をリセットする」前提へ変わりました。

実装では、固定台番を優遇するのではなく、同じ台番として存在している期間内の履歴だけを使います。台番変更直後は、直近21日分の履歴が揃うまで採用条件に一致しない扱いにします。

議事録CSVを直接使った単体バックテストでは、母数は議事録と一致しました。

- 対象日数 309日
- 対象台日 3,708台日
- 合計G数 14,332,643G
- RB 32,851回
- 合計差枚 +97,424枚
- 機械割 100.23%

一方で、議事録本文の点数表をそのまま実装して再計算すると、GPTが併記した採用結果とは一致しませんでした。

|条件|議事録の結果|点数表再計算|
|---|---:|---:|
|毎日1位|309件 / 103.70%|309件 / 103.29%|
|1位＋次点差10点以上|177件 / 105.31%|181件 / 104.26%|
|1位＋危険0|143件 / 105.94%|138件 / 105.63%|
|1位＋65点以上＋強化2個以上＋危険0|104件 / 106.73%|99件 / 105.49%|

このため、実装は件数を無理やり合わせず、議事録本文の点数表を優先しました。採用条件の目安も、実装した点数表をCSVで再計算した値にしています。

## 沖ドキDUOで起きていたこと

沖ドキDUOアンコールは、Webアプリ上で次の結果になっていました。

- 210件
- BB 1/165.3
- RB 1/360.9
- 合成 1/113.4
- 差枚 +107,002
- 機械割 105.0%

一方で、最新議事録の最終結論では、特定日加点を完全に外したうえで、点数の閾値よりも日ごとの順位を重視しています。

議事録で最も安定している条件は次です。

- 毎日上位2位
- 284件
- BB 1/162.1
- RB 1/373.1
- 合成 1/113.0
- 差枚 +150,754
- 機械割 105.73%

ズレの主因は、実装が最新議事録の最終条件ではなく、途中案寄りの次の条件になっていたことです。

- 65点以上
- 沈み核あり
- 危険回避

議事録では、65点以上は足切り・補助条件であり、最終採用条件の主役ではありません。
そのため、既定の採用条件を「上位2位」へ変更しました。

あわせて、点数表も最新議事録の改訂版に合わせています。

- 短期凹み返済は最大39点
- 沈み角度は最大18点
- ローテ・未投入感は最大15点、減点あり
- 連敗・連勝は -7点から+7点
- ボーナス内容の見え方は -9点から+9点
- 近隣取り残されは最大7点
- G数信頼度は -7点から+7点
- 処遇完了リスクは最大24点減点
- 沈み核がない台は最大64点
- 短期深凹みがない台は最大73点
- 14日履歴がない台日は採用条件から除外

その後の照合で、件数は284件に合っているのに内容が悪くなる原因は、高内容日の定義がDUO専用ではなく汎用定義へ落ちていたことだと分かりました。

議事録のDUO高内容日は、G数・合成・RB・差枚・RB比率を点数化し、65点以上かつ2400G以上で判定します。汎用定義のままだと高内容が66件程度に絞られ、議事録定義の314件前後と大きくずれるため、直近高内容回数、前回高内容からの日数、前日高内容後の処遇完了、近隣高内容の評価がすべて別物になります。

修正後は、次をDUO専用の高内容定義として使います。

- G数: 4500G以上30点、3700G以上25点、2400G以上15点、1800G以上8点
- 合成: 1/95以内30点、1/105以内25点、1/115以内20点、1/125以内12点、1/140以内5点
- RB: 1/285以内20点、1/330以内15点、1/400以内10点、1/500以内5点
- 差枚: +3200枚以上20点、+750枚以上15点、0枚以上10点、-500枚以上4点
- RB比率: 30%以上5点、25%以上3点
- 合計65点以上かつ2400G以上を高内容日とする

近隣高内容も、DUOの議事録に合わせて7日ではなく14日集計を参照します。

## マイジャグで起きていたこと

アプリを使わず、議事録CSVを直接使って確認したところ、点数表と採用条件の前段は完全に再現できました。

- 1位のみ: 320件
- 1位かつ3連敗以上: 議事録262件に対し、専用点数表の再現では近い水準
- 1位かつ3連敗以上かつ5日-3,500枚以下: 議事録と完全一致
- 121件
- 954,046G
- RB 1/278.5
- 合成 1/132.2
- 差枚 +141,384
- 機械割 104.94%

ズレの主因は次の3点です。

- 採用条件の3連敗以上が、実連敗ではなく直近4日の負け日数でも通っていた
- 高内容が、マイジャグ専用のG数6,000以上・RB1/270以内・合成1/135以内ではなく、汎用ジャグラー判定に流れていた
- 点数表の前回高内容、大勝ち後の冷却、近隣取り残され、沈み滞在、角度滞在が簡略化されていた

修正後は、次の定義に合わせています。

- 実戦用高内容: G数6,000以上、RB1/270以内、合成1/135以内
- 採用条件の連敗: 実際に前日まで連続で差枚マイナスの3連敗以上
- 採用条件の沈み: 直近5日差枚-3,500枚以下
- 大勝ち後の冷却: 直近で+1,500枚以上出た日からの日数
- 沈み滞在: 5日差枚-3,500枚以下状態の継続日数
- 角度滞在: 5日角度-80枚/1000G以下状態の継続日数

なお、次点差3点以上を加えた本命条件だけは、議事録の82件に対して、独自再現では89件になりました。次点差なしの121件は完全一致しているため、点数表そのものではなく、議事録側の次点差計算または丸め方に差がある可能性が高いです。件数を無理に82件へ寄せる追加条件は入れず、議事録の条件名どおり次点差3点以上で実装しています。

その後、Webアプリ側で103件まで広がっていた原因は、近隣判定の取り方だと特定しました。議事録の「近隣±2台」は同じ機種内の設置順で前後2台を見る意味ですが、実装では台番号が1違いの台だけを近隣として扱っていました。マイジャグは台番号が1028、1030、1031のように飛ぶため、近隣高内容と近隣差枚の点数が議事録と別物になっていました。

この状態をアプリを使わずに再現すると、Webアプリと同じ103件、819,486G、RB 1/281.1、合成 1/132.6、差枚 +121,762、機械割 104.95%になりました。近隣を同じ機種内の設置順±2台へ戻すと、次点差なしの前段は議事録と同じ121件、954,046G、RB 1/278.5、合成 1/132.2、差枚 +141,384、機械割 104.94%になります。

一方で、次点差3点以上まで入れた最終条件は、設置順±2台でも89件で、議事録の82件とは完全一致しません。この差は点数表や近隣判定ではなく、議事録側の次点差の丸め方、または当時の検証コード側の細部差と見ています。今回は、件数を82件へ無理に合わせる隠し条件は追加せず、議事録本文に書かれている条件どおり実装する方針にしています。

- 70点以上
- 次点差30点以上

議事録の結果は次でした。

- 47件
- RB 1/276.6
- 合成 1/132.8
- 平均差枚 +702
- 機械割 103.30%

アプリを使わず、議事録CSVを直接使って確認したところ、ズレの主因は次の3点でした。

- 直近3日急沈みは議事録上「最大10点」なのに、実装では3日角度点と3日差枚-1,800枚以下の4点を足して最大14点になっていた
- 高内容が、ガールズ専用の「G数4,000以上、RB25回以上、RB1/281以内、合成1/128以内」ではなく汎用判定に流れていた
- 前回高内容からの空き、直近7日高内容回数、前日高内容の不発・大出し判定が、ガールズ専用高内容ではなく共通寄りの判定を見ていた

議事録CSVで再計算すると、直近3日急沈みを最大10点に直すだけで、70点以上の台数は議事録と同じ73件になりました。

最終条件は、議事録47件に対して単体再計算では50件でした。

- 50件
- RB 1/270.1
- 合成 1/131.3
- 差枚 +38,231
- 機械割 103.55%

3件の差は、次点差の丸め方や同点処理の細部差と見ています。件数を47件へ無理に合わせる隠し条件は入れず、議事録本文の「1位、70点以上、次点差30点以上」をそのまま使います。

修正後は、次の定義に合わせています。

- 高内容: G数4,000以上、RB25回以上、RB1/281以内、合成1/128以内
- 直近3日急沈み: 3日角度点と3日差枚-1,800枚以下のうち強い方だけを使い、最大10点
- 前回高内容からの空き: ガールズ専用高内容から数える
- 直近7日高内容回数: ガールズ専用高内容で数える
- 前日高内容の不発・大出し: ガールズ専用高内容で判定する

- 危険条件が多くない

議事録の結果は次でした。

- 94件
- RB 1/288.6
- 合成 1/133.0
- 差枚 +87,677
- 機械割 104.73%

アプリを使わず、議事録CSVを直接使って確認したところ、同じ点数表と採用条件で次の結果になりました。

- 97件
- RB 1/291.7
- 合成 1/134.2
- 差枚 +82,667
- 機械割 104.36%

議事録との差は3件で、方向性はかなり近いと判断しています。

ズレの主因は次の4点でした。

- 議事録では設定列を最終ロジックに使わない前提なのに、実装では共通の高内容判定が設定推定由来の履歴を一部見ていた
- 目標高内容が、ミスター専用の「G数5,000以上、RB1/290以内、合成1/135以内」ではなく汎用判定に流れていた
- 強内容が、ミスター専用の「RB25回以上、RB1/260以内、合成1/140以内」ではなく汎用の強内容判定になっていた
- 議事録にある30日累計、長期放置危険、近隣取り残されが実装側で不足していた
- 議事録では最初の30営業日をウォームアップ除外しているのに、採用条件側に30日履歴必須が入っていなかった

修正後は、次の定義に合わせています。

- 目標高内容: G数5,000以上、RB1/290以内、合成1/135以内
- 強内容: RB25回以上、RB1/260以内、合成1/140以内
- 30日累計: 直近30日差枚-2,700枚以下を返済未完了の補助として使う
- 長期放置危険: 7日沈み状態7営業日以上、または30日沈み状態7営業日以上を危険条件に入れる
- 近隣取り残され: 近隣高内容あり、または近隣7日差枚プラスで自台7日差枚マイナスを補助加点に使う
- 採用条件: 30日履歴あり、1位、60点以上、次点差10点以上、危険条件1個以下

件数を94件へ無理に合わせる隠し条件は入れず、議事録本文の条件をそのまま使います。

## 他機種を直す時の手順

1. 議事録の採用条件とバックテスト結果を引用する
2. Webアプリの同条件結果を控える
3. 議事録へ渡したCSVで、アプリを使わない単体バックテストを行う
4. 単体バックテストが議事録に近いか確認する
5. 近ければ、Webアプリ実装側の問題を探す
6. 近くなければ、議事録条件の読み取りや点数式の再現を疑う
7. 点数計算、採用条件、集計期間、履歴の持ち方を別々に確認する
8. 修正後は、件数だけでなく内容の質も確認する

## 合格ラインの考え方

完全一致だけを目標にすると、CSVとWebアプリ側のデータ差や期間端の違いで作業が止まりやすくなります。

次の条件を満たせば、基本的には合格候補として扱います。

- 件数が大きくずれていない
- 合計G数が大きくずれていない
- RB、合成、機械割の方向性が議事録と近い
- 差枚の水準が大きく崩れていない
- 条件を広げたり狭めたりして無理に合わせていない

ただし、件数が合っていてもRBや合成が大きく違う場合は、別条件を拾っている可能性が高いので不合格です。
