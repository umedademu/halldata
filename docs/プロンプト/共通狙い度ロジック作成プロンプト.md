# 店舗共通狙い度ロジック作成プロンプト

## 最重要ルール

このプロンプトの最終目的は、分析レポートではなく、あとでCodexがWebアプリへ迷わず実装できる「実装用の正本」を作ることです。

回答本文では仮説検証や途中経過を書いて構いませんが、実装に使ってよい内容は、回答の最後に出す **実装用正本** と **Codex貼り付け用 実装依頼** に集約してください。

途中で試した条件、比較用の条件、失敗した条件、過去データに合わせすぎた疑いがある条件は、最終採用条件と混ざらないようにしてください。

今回の回答は、後でCodexがそのままWebアプリへ実装します。

そのため、**条件式、該当日付・機種名・台番一覧、バックテスト集計値が回答内で一致していること**を、最終回答前に必ず自己検算してください。

以下の3つが1つでもズレる条件は、Webアプリへ通常採用してはいけません。

- 条件式から抽出した件数
- 該当日付・機種名・台番一覧の件数
- バックテスト集計表の選択台数、総G数、BB、RB、差枚

ズレた条件は、強そうに見えても `未採用` または `参考表示` にしてください。

ズレた条件を、あとでCodexがしらみつぶしに調整して合わせる前提にしないでください。

最終回答には、必ず **回答内整合性チェック表** を出してください。

| 条件名 | 採用区分 | 条件式抽出件数 | 該当一覧件数 | 集計表の選択台数 | 総G数一致 | BB一致 | RB一致 | 判定 |
|---|---|---:|---:|---:|---|---|---|---|

判定は `一致・通常採用可`、`一致・弱め採用可`、`一致・参考表示`、`一致・見送り条件として採用可`、`不一致・未採用` のどれかにしてください。

`不一致・未採用` の条件は、Codex貼り付け用 実装依頼に「実装しない条件」としてだけ載せてください。

## このプロンプトで作りたいもの

既存の機種別ロジックは、その店舗の1機種だけの過去データを見て、ChatGPTが「こういう台に座ると高設定に座りやすい」と判断したものです。

しかし、少数設置機種ではデータ件数が少なく、機種別ロジックが過去データに合いすぎるリスクがあります。特に、設置台数が少なく、イベント日にしか高設定が入りにくい機種では、単機種だけの分析だと未来予測として弱くなる可能性があります。

そこで、このプロンプトでは、機種別ロジックとは別に、対象店舗の主要機種を横断して見た **店舗共通スコア** を作ってください。

目的は、機種別ロジックを置き換えることではありません。

目的は、毎日の狙い度ランキングで、以下のように判断できるようにすることです。

- 機種別スコアだけが強い台
- 店舗共通スコアだけが強い台
- 機種別スコアも店舗共通スコアも強い台
- 機種別スコアは強いが、店舗共通では危険な台

特に重視したいのは、**「機種別スコアも強く、店舗共通スコアも強い台」を、より信頼度の高い本命として抽出すること**です。

設定師は基本的に店舗全体の設定配置を考えるため、機種ごとの差はあっても、投入間隔、冷却期間、凹みの扱い、据え置きの有無、出し切り後の扱いなどには店舗全体で共通するクセがあるはずです。

この店舗全体のクセを、全機種共通の同じ物差しで点数化してください。

## 絶対に守ること

このプロンプトで作るのは、**ジャグラー系共通ロジック** や **AT・スマスロ系共通ロジック** ではありません。

このプロンプトで必ず作るのは、**店舗全体に共通する設定師のクセを点数化する、全日共通の店舗共通スコア** です。

通常日とイベント日で台ごとの履歴、沈み、高内容間隔、処遇済み後の扱いなどの効き方が明確に違う場合だけ、全日共通の店舗共通スコアに加えて、通常日専用ロジックとイベント日専用ロジックを補助として作ってください。

ただし、その場合でも、日付そのものを点数化するのではなく、通常日・イベント日それぞれの母集団の中で、全機種共通の同じ考え方を使ってください。

以下は禁止です。

- ジャグラー系専用の共通スコアを作ること
- AT・スマスロ系専用の共通スコアを作ること
- `EV_J_...`、`EV_AT_...` のように、機種タイプ別の採用条件を主軸にすること
- ジャグラー系だけで強い条件を、店舗共通ロジックとして通常採用すること
- AT・スマスロ系だけで強い条件を、店舗共通ロジックとして通常採用すること
- 機種名や固定台番そのものを直接優遇すること
- 単機種だけで強いクセを、店舗共通のクセとして扱うこと

分けてよいのは、以下だけです。

- 過去の「高内容だったか」を判定する材料
- バックテスト結果を読む時の重視指標
- 結果表をジャグラー系、AT・スマスロ系、その他に分けて確認すること

つまり、ジャグラー系とAT・スマスロ系で違ってよいのは、**高内容判定の入口** と **結果確認の見方** だけです。

いったん `高内容だったか`、`強高内容だったか`、`前回高内容から何日か`、`直近で処遇済みか` のような共通変数へ変換した後は、全機種で同じ点数式、同じ危険条件、同じ採用条件を使ってください。

## 入力として渡すもの

- 対象店舗の主要10機種分のCSV
- 各機種を単体で分析したChatGPT回答または議事録
- 店舗や日付に関する議事録
- イベント日、通常日、対象期間などの補足情報

各機種につき、原則として「CSV」と「単機種分析の回答または議事録」が1つずつあります。

各CSVには、原則として `特定日` 列があります。

通常日とイベント日は、CSVの `特定日` 列を正として扱ってください。

- `特定日` が `はい` の行をイベント日として扱う
- `特定日` が `いいえ` の行を通常日として扱う
- `特定日` 列が見つからない場合は、分析を始める前に不足情報として明記する

`3の付く日`、`6の付く日`、`月初`、`月末`、`曜日`、`末尾0の日`、`ゾロ目の日` など、CSV外の固定日付ルールを推測して使わないでください。

まず、どの機種にどのCSVと議事録が対応しているかを確認してください。不足、重複、対応不明のファイルがある場合は、分析を始める前に明記してください。

このプロンプトは、単機種ロジック生成用プロンプトを別ファイルとして添付しない前提で作っています。このプロンプト単体で、店舗共通ロジック生成に必要な前提をすべて満たすものとして扱ってください。

## 未来情報の禁止

着席対象日の当日結果として初めて分かる差枚、G数、BB、RB、合成、ブドウ、設定、機械割などは、狙い度の入力に使わないでください。

過去日を使って翌営業日を予測する前提で、予測時点で分かっている情報だけを使ってください。

既に計算済みの最終狙い度、店舗共通順位、次点差など、出力側の値を、店舗共通スコアの入力条件として使わないでください。

ただし、店舗共通スコアを計算した後に、同一機種内順位や次点差を使って表示・採用条件を作ることは可能です。その場合は、必ず「スコア計算後に使う値」と明記してください。

## 日付の対応関係

このプロンプトでは、日付の意味を必ず以下のように固定してください。

| 用語 | 意味 | 例 |
|---|---|---|
| スコア日 | ここまでに確定した過去データを使ってスコアを計算する基準日 | 5/14 |
| 着席対象日 | 実際に座るかどうかを判断したい日。原則としてスコア日の翌営業日 | 5/15 |
| 実績日 | バックテストで差枚、G数、BB、RB、機械割などを集計する日。原則として着席対象日と同じ日 | 5/15 |

最重要の前提として、**5/14のスコアは、5/14に座るべき度ではなく、5/15に座るべき度です。**

つまり、あるスコア日の店舗共通スコアは、そのスコア日までのデータを材料にして、翌営業日に座る台を決めるための点数です。

例:

- 5/14までのデータを使って、5/14の店舗共通スコアを計算する
- その5/14の店舗共通スコアは、翌営業日である5/15に座るべき度を表す
- バックテストでは、5/14のスコア、順位、採用条件と、5/15の実績を照合する
- 5/15の差枚、G数、BB、RB、合成、ブドウ、設定、機械割は、5/14のスコア計算には絶対に使わない

回答内では、必ず「スコア日」「着席対象日」「実績日」を分けて書いてください。

`5/14スコア → 5/15実績` のように、スコア日と実績日の対応が分かる形でバックテスト結果を出してください。

Webアプリへ入力する期間がスコア日基準で、回答内バックテストの実績日範囲と1営業日ずれる場合は、その理由を必ず明記してください。

## 通常日・イベント日の扱い

日付そのものは、店舗共通スコアの直接加点や直接減点に使わないでください。

以下のような点数項目は禁止です。

- `特定日だから+10点`
- `イベント日だから+10点`
- `月初だから+5点`
- `月末だから+5点`
- `曜日が◯曜日だから+5点`
- `ゾロ目の日だから+5点`

通常日とイベント日を分ける目的は、日付そのものに点数を付けることではありません。

目的は、通常日とイベント日で、設定師の台ごとの使い方が明確に違うかを確認することです。

まず、必ず全日共通の店舗共通ロジックを作ってください。

そのうえで、CSVの `特定日` 列を使い、通常日とイベント日で以下の効き方が明確に違うかを検証してください。

- 高内容台が入る前の履歴パターン
- 連敗、沈み、返済未完了、処遇完了の効き方
- 前回高内容からの間隔
- 前日高内容の据え置き、不発据え置き、出た後の扱い
- 近隣や同機種内順位の効き方
- ボーナス内容、G数信頼度、低稼働の扱い
- 採用条件のバックテスト結果

共通ロジック固有の追加確認として、機種別スコアと店舗共通スコアの掛け合わせ結果も確認してください。

通常日とイベント日で差が明確で、件数が少なすぎず、複数機種・複数期間で再現性がある場合だけ、全日共通ロジックとは別に、通常日専用ロジックとイベント日専用ロジックを作ってください。

差が弱い場合や件数不足で過去データに合わせすぎる危険が高い場合は、通常日専用ロジックとイベント日専用ロジックは作らず、全日共通ロジックだけを提出してください。その場合は、分けない理由を短く書いてください。

通常日専用ロジックやイベント日専用ロジックを作る場合でも、点数項目に `イベント日だから加点` のような項目を入れてはいけません。

通常日・イベント日で母集団を分けたうえで、その中の台ごとの履歴差、沈み、返済未完了、処遇完了、高内容間隔、G数信頼度などを使って点数式と採用条件を作ってください。

## 高内容判定の正規化

店舗共通スコアを作る前に、各機種の過去データを、全機種で使える共通変数へ変換してください。

この段階だけは、機種タイプによって判定材料を変えて構いません。

### ジャグラー系

ジャグラー系は、CSVから設定判別に使える情報が比較的多いため、過去の高内容判定では以下の優先順を使ってください。

- 最優先: RB率
- 次点: ボーナス確率、合成確率
- 補助: 機械割、差枚

優先順位は、原則として以下です。

- RB率 ＞ ボーナス確率、合成確率 ＞ 機械割、差枚

差枚や機械割だけが強い台を、RB率が弱いにもかかわらず強い高内容として扱いすぎないでください。

### AT機、スマスロ系

カバネリ、モンキーターン、北斗転生、L北斗の拳、ヴァルヴレイヴ、東京喰種、沖ドキ、ミリオンゴッドなどのAT機やスマスロ系は、CSV上のボーナス確率だけで設定判別するのが難しいため、過去の高内容判定では以下の優先順を使ってください。

- 最優先: 機械割、差枚
- 補助: G数、勝率、安定してプラスになっているか
- 参考以下: ボーナス確率

優先順位は、原則として以下です。

- 機械割、差枚 ＞＞ ボーナス確率

AT機やスマスロ系では、ボーナス確率を強い設定判別材料として扱わないでください。

### 共通変数へ変換する

機種タイプごとの判定を使って、少なくとも以下の共通変数を作ってください。

| 共通変数 | 意味 |
|---|---|
| `isHighContent` | その過去日が、その機種タイプ基準で高内容だったか |
| `isStrongHighContent` | その過去日が、その機種タイプ基準で強高内容だったか |
| `daysSinceHighContent` | 前回高内容からの営業日数 |
| `daysSinceStrongHighContent` | 前回強高内容からの営業日数 |
| `highContentCount7` | 直近7営業日の高内容回数 |
| `strongHighContentCount7` | 直近7営業日の強高内容回数 |
| `prevHighContent` | 前日が高内容だったか |
| `recentOvertreated` | 直近で出し切り、または処遇済みと見なせるか |
| `sinkScore` | 直近の沈み具合を全機種で比較できる形に正規化した値 |
| `lossStreak` | 連敗数 |
| `historyDays` | その台の履歴として使える営業日数 |
| `lowInfoFlag` | 履歴不足や低稼働で信頼度が低いか |

ここで重要なのは、ジャグラー系のRB率やAT・スマスロ系の機械割を、そのまま店舗共通スコアへ別々に入れることではありません。

それらは、あくまで `isHighContent` や `isStrongHighContent` を作るための入口です。

店舗共通スコア本体では、上記の共通変数を使って、全機種に同じ点数式を適用してください。

## 店舗共通スコアで検証してほしいクセ

以下は、設定師のクセとして考えられる典型例です。

ただし、これらに無理に当てはめる必要はありません。

データ上で弱いものは不採用にしてください。

## ローテーション系

### ローテーションで入れる店

直近で高設定を入れていない台に、順番に高設定を入れるパターン。

前回高内容からの日数、直近の高内容回数、一定期間内の投入間隔などを検証してください。

### ずっと高設定を入れない台がある店

ローテーション狙いをする客心理の逆をついて、同じ台に長期間高設定を入れないパターン。

長期間空いていることがプラスなのか、むしろ放置台としてマイナスなのかを検証してください。

---

## ヘコみ・上げ狙い系

### ヘコみに入れる店

直近の差枚が悪い台に高設定を入れるパターン。

前日だけを見るのではなく、複数の期間で検証してください。

どの期間の凹みを店が意識していそうか、データから探索してください。

### ヘコみに入れない店

ヘコみ台狙いをする客心理の逆をついて、凹み台に入れる確率が低いパターン。

凹みが深すぎる台、稼働が少なすぎる台、長期間沈みっぱなしの台が本当に狙えるのかを検証してください。

### よく出ている台に入れる店

ヘコみ狙いの逆をついて、直近で出ている台に入れるパターン。

ただし、単に出た台を据えるのか、それとも「まだ処遇完了していない出方」の台だけを使うのかを分けて検証してください。

---

## 連続投入・据え置き系

### 連続で同じ台に入れる店

同じ台に高設定を連続投入するパターン。

ただし、連続投入が何回まで有効なのかは決め打ちしないでください。

データから、

- 連続投入されやすい条件

- 連続投入されにくくなる条件

- 何回目以降に弱くなるか

- 不発後と大きく出た後で違いがあるか


を探索してください。

### 前日高設定で不発の台を据え置く店

高設定っぽい内容なのに差枚が伸びなかった台を、翌日もう一度使うパターン。

ただし、「不発」の定義は固定せず、ボーナス内容、差枚、G数、合成確率、RB率などから探索してください。

### 前日高設定でしっかり出た台を据え置く店

不発据え置き狙いの逆をついて、しっかり出た高設定台を翌日も使うパターン。

ただし、何枚以上出たら据え置きにくいのか、あるいはどの程度出ても据え置くのかは、データから探索してください。

---

## 稼働・見え方系

### 稼働が多い台を優遇する店

直近のG数が多い台、つまり客に見られている台に高設定を入れるパターン。

どの期間のG数が効いているか、どの程度のG数が必要かをデータから探索してください。

### 稼働が少ない台を優遇する店

あまり回されていない台に高設定を入れるパターン。

ただし、低稼働すぎる台はデータとして信頼できない可能性があります。

低稼働がプラスなのか、放置のサインなのかを分けて検証してください。

### 当たり回数が少ない台を返す店

直近でBB/RBなどのボーナス回数が少なく、客から見て印象が悪い台に高設定を入れるパターン。

ただし、当たり回数だけでなく、G数に対するボーナス確率として評価してください。

---

# 追加で検証してほしい重要観点

ここから先は、特に深掘りしてほしい追加観点です。

ただし、ここでも具体的な閾値は決め打ちせず、CSVデータから探索してください。

## 沈み滞在

直近の一定期間における合計差枚が、一定ライン以下の状態にどれくらい滞在しているかを見てください。

単に前日負けた台ではなく、一定期間ずっと返されていない台を店が返す可能性があります。

検証してほしいことは以下です。

- どの期間の合計差枚が効いているか

- どの程度沈んだ状態が効いているか

- 何日間その状態に滞在すると強くなるか

- 長く沈みすぎると逆に弱くなるか

- 沈み滞在はメイン点数に入れるべきか、サブ条件にするべきか


## 差枚の角度

単純な差枚マイナスではなく、G数に対してどれくらい急角度で沈んでいるかを見てください。

たとえば、一定期間の合計差枚を同期間の合計G数で割るような考え方です。

検証してほしいことは以下です。

- どの期間の角度が効いているか

- 急角度の沈みが強いのか

- 緩やかな沈みが強いのか

- G数が少ないだけのマイナスをどう扱うべきか

- 角度はメイン点数に入れるべきか、サブ条件にするべきか


## 返済未完了

一度出た後でも、過去の負けを返し切っていない台をもう一度使うパターンを検証してください。

単に「出たから終わり」ではなく、一定期間の累計差枚で見たときに、まだ未処遇と見なされる台があるかを確認してください。

検証してほしいことは以下です。

- どの期間の累計差枚で見るべきか

- 出た後でも再投入される台の共通点は何か

- ボーナス内容が強い台ほど再投入されやすいか

- 出玉だけ強い台と、ボーナス内容まで強い台で違いがあるか


## 処遇完了

直近で十分に出た台、見せ場を作り切った台、累計差枚が大きく戻った台を、店が「もう返した台」とみなして外すパターンを検証してください。

検証してほしいことは以下です。

- どの程度出ると処遇完了と見なされやすいか

- 何日間の累計差枚が戻ると弱くなるか

- 高内容で出た台と、内容は弱いが出ただけの台で違いがあるか

- 処遇完了は減点にするべきか、見送り条件にするべきか


## 大きく出た翌日の扱い

高内容かつ大きく出た台を翌日も使う場合と、使わない場合の違いを検証してください。

ただし、何枚以上を「大きく出た」と見るかは決め打ちしないでください。

データから、どの出玉帯を境に挙動が変わるのかを探索してください。

検証してほしいことは以下です。

- どの程度出ると翌日弱くなるか

- どの程度出ても翌日残るパターンがあるか

- 出た日のRB率や合算確率が強い場合は残りやすいか

- 出る前の凹みや連敗が残っている場合は残りやすいか

- 出た後の累計差枚がまだ弱い場合は残りやすいか

- 前日以前に見せ場があった台は落ちやすいか


## ボーナス内容の本物感

Aタイプ・ジャグラー系では、出玉だけでなくボーナス内容を重視してください。

特に、以下を分けて見てください。

- RB率が強い台

- 合算確率が強い台

- BBに寄って出ただけの台

- RBは強いが差枚が伸びなかった台

- 合算もRBも強い台

- G数が少なくて判断しにくい台


RB率だけでなく、合算確率も必ず見てください。

## 連敗数

現在連敗数が設定投入に関係しているかを検証してください。

ただし、具体的な連敗数はこちらから指定しません。

どの連敗数から強くなるのか、どの連敗数で弱くなるのか、データから探索してください。

検証してほしいことは以下です。

- 連敗数は多いほど強いのか

- 特定の連敗数にピークがあるのか

- 長期連敗は放置台になっていないか

- 稼働量によって連敗数の意味が変わるか

- 連敗数はメイン点数に入れるべきか、サブ条件にするべきか


## 最低限のG数

凹み、連敗、不発、RB内容などの条件があっても、G数が少なすぎる場合は信頼度が低い可能性があります。

どの程度のG数があれば、前日以前のデータとして信頼できるのかを探索してください。

検証してほしいことは以下です。

- 前日G数の最低ライン

- 直近複数日合計G数の最低ライン

- 低G数の凹みは使えるのか

- 高G数で凹んだ台の方が強いのか

- 高G数で出た台は処遇完了になりやすいのか


## 列・近隣台・島の見せ場

同じ列、近い台番、同じ島で最近どれだけ見せ場があったかによって、投入位置が変わる可能性があります。

ただし、固定台番優遇にならないようにしてください。

あくまで、

- 近隣台の直近状況

- 同じ列の直近高内容回数

- 近い台番で見せ場が出た後かどうか

- 周辺が出ている中で取り残されている台かどうか


のように、汎用的な形で検証してください。

---

店舗共通ロジックでは、上記の典型例を、単機種だけで強いクセとしてではなく、複数機種を横断して共通しているかという観点で検証してください。

また、機種別スコアが強い台の中でも店舗共通スコアが強い台の成績がさらに良くなるか、機種別スコアが強くても店舗共通の危険条件に当たる台は成績が落ちるかも確認してください。

## 作成してほしいもの

### 1. 入力ファイル確認と機種別要約

最初に、入力されたファイルを機種ごとに整理してください。

以下を表でまとめてください。

- 機種名
- CSVファイル名
- 議事録または単機種分析ファイル名
- 機種タイプ
- 過去の高内容判定で最優先する指標
- CSVから見える主な事実
- 議事録で提案されている主な単機種クセ
- 店舗共通ロジックに使えそうな要素
- 店舗共通ではなく単機種固有に留めるべき要素

### 2. 店舗共通スコアの100点満点計算式

まず、全機種に同じ構造で使う、全日共通の店舗共通スコアを作ってください。

名前は `storeCommonScore` としてください。

通常日とイベント日で明確な差があり、別ロジックを作る場合は、補助ロジックとして以下の名前を使ってください。

- 通常日専用: `storeCommonScoreNormalDay`
- イベント日専用: `storeCommonScoreEventDay`

通常日専用、イベント日専用を作らない場合は、その理由を明記してください。

以下を必ず含めてください。

- 使用する共通変数の一覧
- 各共通変数の意味
- 点数の加点、減点、上限、下限
- 100点満点へ丸める方法
- 全日共通ロジックを必ず作ること
- 通常日とイベント日で点数式や採用条件を分ける必要があるか
- 分ける場合でも、日付そのものを直接加点や直接減点に使わないこと
- 分ける場合でも、ジャグラー系用、AT系用のような機種タイプ別点数式にはしないこと
- 履歴不足台をどう扱うか
- 店休日、欠損日、全台G数0の日をどう扱うか
- 台番変更、増台、減台、島変更があった場合に履歴をどう扱うか

店舗共通スコアの条件式には、原則として `machineType == "JUGGLER"` や `machineType == "AT_SMART"` のような分岐を入れないでください。

機種タイプ分岐を使ってよいのは、高内容判定を共通変数へ変換する入口だけです。

### 3. 店舗共通の危険条件、見送り条件

全機種に同じ構造で使える危険条件と見送り条件を作ってください。

以下を分けてください。

- 店舗共通スコアを下げる危険条件
- 採用対象から外す見送り条件
- 参考表示に落とす条件

特に、以下を検証してください。

- 直近高内容直後
- 強高内容の短期集中
- 出し切り後
- 深すぎる沈み
- 長期連敗
- 履歴不足
- 低稼働で判断材料が足りない台
- 機種別スコアは強いが、店舗共通では危険な台

### 4. 店舗共通採用条件

点数式とは別に、実戦で使う店舗共通採用条件を作ってください。

ただし、採用条件も全機種共通の構造にしてください。

以下の4分類で整理してください。

- 通常採用
- 弱め採用
- 参考表示
- 見送り

未採用条件も、実装しない条件として理由だけ残してください。

| 区分 | 意味 | Codexの扱い |
|---|---|---|
| 通常採用 | 店舗共通条件として実装してよい | 主要条件として実装する |
| 弱め採用 | 通常採用より期待値は落ちるが、補助候補として使える | 補助条件として実装する |
| 参考表示 | 方向性はあるが、件数不足や定義不足がある | 参考条件としてだけ表示し、通常採用の主軸にしない |
| 見送り | 条件に当たったら避ける | 見送り条件として実装する |
| 未採用 | 試したが弱い、または再現性がない | 実装しない。理由だけ残す |

採用条件は、以下の形式で機械的に書いてください。

```text
条件名：
採用区分：通常採用 / 弱め採用 / 参考表示 / 見送り / 未採用
条件式：
店舗共通スコアへの影響：
期待値表示：
対象機種：
対象日数：
選択台数：
総G数：
BB：
RB：
BB確率：
RB確率：
合成確率：
平均差枚：
機械割：
勝率：
該当日付・機種名・台番一覧：
実装上の注意：
```

条件式は、文章ではなく、できるだけ以下のように書いてください。

```text
historyDays >= 21 && storeCommonScore >= 80 && storeCommonRiskCount == 0 && storeCommonRankInMachine <= 2
```

条件式として数値化できないものは、実装候補ではなく参考仮説として扱ってください。

### 5. 機種別ロジックとの掛け合わせ条件

店舗共通スコアは、既存の機種別ロジックを置き換えるものではありません。

必ず、機種別ロジックとの使い分けと掛け合わせ条件を作ってください。

以下を提案してください。

- 機種別スコアだけが強い時の扱い
- 店舗共通スコアだけが強い時の扱い
- 機種別スコアも店舗共通スコアも強い時の扱い
- 機種別スコアは強いが、店舗共通危険条件に当たる時の扱い
- 店舗共通スコアは強いが、単機種ロジックが弱い時の扱い
- 通常日とイベント日で、別の店舗共通スコアや別の採用条件を作るべきか
- 最終的な狙い度ランキングで、機種別スコアと店舗共通スコアをどう並べて表示するべきか

例として、以下のような掛け合わせ条件を検証してください。

- 機種別1位かつ店舗共通1位
- 機種別上位2位以内かつ店舗共通上位2位以内
- 機種別スコア80点以上かつ店舗共通スコア80点以上
- 機種別スコアは高いが店舗共通危険条件に該当
- 店舗共通スコアは高いが機種別スコアが低い

この掛け合わせ条件は、店舗共通スコアの役割を明確にするために必要です。

### 6. バックテスト結果

以下の単位でバックテストしてください。

- 全機種合算
- 機種別
- ジャグラー系、AT・スマスロ系、その他の区分別
- 通常日
- イベント日
- 前半期間
- 後半期間
- 月別
- 店舗共通採用条件別
- 機種別スコアとの掛け合わせ条件別
- 通常採用、弱め採用、参考表示、見送り別

各結果には、少なくとも以下を出してください。

- 件数
- 勝率
- 合計差枚
- 平均差枚
- 合計G数
- BB率
- RB率
- 合成確率
- 機械割
- 平均設定

結果を評価する時は、以下のように読んでください。

- ジャグラー系は、RB率、合成確率、機械割、差枚を見る
- AT・スマスロ系は、機械割、差枚を主に見る
- AT・スマスロ系では、ボーナス確率を設定判別の主軸として扱わない
- 全機種合算では、特定機種や特定タイプだけに偏っていないかを必ず見る
- 月別結果は、過去データへの合わせすぎ確認として見るだけにし、月初、月末、曜日そのものを点数項目にしない

ただし、結果の読み方を分けることと、点数式や採用条件を機種タイプ別に分けることは別です。

点数式と採用条件は、店舗共通の同じ構造を維持してください。

## 過剰な当てはめ対策

以下を必ず確認してください。

- 前半期間だけ強く、後半期間で崩れていないか
- 一部の月だけに偏っていないか
- 一部の機種だけに偏っていないか
- ジャグラー系だけ、またはAT・スマスロ系だけでしか強くない条件になっていないか
- 少数設置機種だけに引っ張られていないか
- 件数が少なすぎないか
- 条件が細かすぎないか
- 勝率だけでなく、差枚、機械割、ジャグラー系ではRB・合成でも裏付けがあるか
- 機種別ロジックの内容をなぞっただけになっていないか
- 不採用にしたクセと、その理由を明記しているか

通常採用にできるのは、複数機種、複数期間、通常日またはイベント日のどちらかで十分な件数があり、条件式、変数定義、バックテスト結果、該当日付・機種名・台番一覧がそろっていて、Webアプリで照合できる条件だけです。

- 条件式、該当日付・機種名・台番一覧、バックテスト集計値の回答内整合性チェック表
- コミットメッセージ案

Codex貼り付け用 実装依頼には、次の実装完了条件を必ず強調して入れてください。

- Webアプリ上で実際にバックテストを回し、回答内に書いた採用条件ごとの選択台数、総G数、BB確率、RB/REG、合算、平均差枚、機械割と照合する
- Webアプリ側のバックテスト結果と回答内のバックテスト結果が、実用上許容できる範囲まで一致しない限り、実装完了扱いにしない
- ここでいう許容範囲は、選択台数、総G数、BB数、RB数などの母数がほぼ一致し、確率、機械割、平均差枚の差が丸め誤差や表示単位差で説明できる程度とする
- 回答内では整合しているのにWebアプリで一致しない場合は、条件式、最新日除外、未来情報除外、対象機種名、台番、履歴計算、通常日/イベント日の分岐、集計期間の違いを疑い、Webアプリ上で再検証しながら修正する
- 回答内の条件式、該当日付・機種名・台番一覧、集計表が最初から矛盾している条件は、Webアプリ側で無理に補正して合わせない
- 採用条件のラベル名や期待値表示だけを写して終わらせず、実際にWebアプリのバックテストで再現できる条件式に落とし込む
- 該当日付・機種名・台番一覧がある場合は、Webアプリの該当台と突き合わせる
- 回答本文の途中に出した条件と、最後の実装用正本の条件が矛盾する場合は、最後の実装用正本を正として扱う

Codex貼り付け用 実装依頼は、必ず1つのコードブロックにまとめてください。

そのコードブロックだけをコピーすれば、Codexへの実装依頼として成立する文章にしてください。
