# 狙い台ロジック作成プロンプト

# 最重要ルール

このプロンプトの最終目的は、分析レポートではなく、あとでCodexがWebアプリへ迷わず実装できる「実装用の正本」を作ることです。

回答本文では仮説検証や途中経過を書いて構いませんが、実装に使ってよい内容は、回答の最後に出す **実装用正本** と **Codex貼り付け用 実装依頼** に集約してください。

途中で試した条件、比較用の条件、失敗した条件、過剰最適化の疑いがある条件は、最終採用条件と混ざらないようにしてください。

## 無駄な照合作業を防ぐ最重要ルール

今回の回答は、後でCodexがそのままWebアプリへ実装します。

そのため、**条件式、該当日付・台番一覧、バックテスト集計値が回答内で一致していること**を、最終回答前に必ず自己検算してください。

以下の3つが1つでもズレる条件は、Webアプリへ通常採用してはいけません。

- 条件式から抽出した件数
- 該当日付・台番一覧の件数
- バックテスト集計表の選択台数、総G数、BB、RB、差枚

ズレた条件は、強そうに見えても `未採用` または `参考表示` にしてください。

ズレた条件を、あとでCodexがしらみつぶしに調整して合わせる前提にしないでください。

特に、次のような回答は禁止です。

- 集計表は条件Aで作ったが、最終条件式は条件Bに変わっている
- 条件式では拾えない台を、該当一覧にだけ含めている
- 該当一覧にない台を、集計表に含めている
- 条件式の変数定義が曖昧で、同じ件数を再現できない
- 出力上限を理由に該当一覧を省略した条件を、通常採用として扱う

最終回答には、必ず **回答内整合性チェック表** を出してください。

| 条件名 | 採用区分 | 条件式抽出件数 | 該当一覧件数 | 集計表の選択台数 | 総G数一致 | BB一致 | RB一致 | 判定 |
|---|---|---:|---:|---:|---|---|---|---|

判定は `一致・通常採用可`、`一致・参考表示`、`不一致・未採用` のどれかにしてください。

`不一致・未採用` の条件は、Codex貼り付け用 実装依頼に「実装しない条件」としてだけ載せてください。

## 実装用正本で必ず固定すること

最後の実装用正本では、以下を表で固定してください。

- 対象店舗
- 対象機種
- 回答内バックテストの実績日範囲
- Webアプリへ入力すべき予測日基準の開始日と終了日
- Webアプリの「設定分布を表示」をONにするかOFFにするか
- 最新日として除外した日
- 履歴計算に使い始めた日
- 台番変更や設置変更による履歴リセット日
- 高内容、準高内容、強高内容の数値定義
- 100点満点ロジックの点数式
- 強化条件
- 危険条件
- 見送り条件
- Webアプリへ通常採用してよい条件
- 参考表示に留める条件
- 未採用にする条件
- 自由度MAX条件のうち、通常採用条件より優先するもの

特に、回答内バックテストの「実績日」と、Webアプリへ入力する「予測日基準の日付」は必ず分けてください。

Webアプリが翌営業日実績を集計する前提の場合は、回答内実績日とWebアプリ入力期間が1日ずれる可能性があります。このずれを必ず確認し、実装用正本に明記してください。

## 採用可否の区分

採用条件は、最後に必ず次の4区分へ分けてください。

| 区分 | 意味 | Codexの扱い |
|---|---|---|
| 通常採用 | Webアプリへ条件として実装してよい | 初期条件または選択肢として実装する |
| 参考表示 | 方向性は強いが、件数不足や定義不足がある | 参考条件としてだけ表示し、通常採用の主軸にしない |
| 見送り | 条件に当たったら避ける | 見送り条件として実装する |
| 未採用 | 試したが弱い、または再現性がない | 実装しない。理由だけ残す |

「強そう」「使えそう」という自然言語だけで通常採用にしないでください。

通常採用にできるのは、条件式、変数定義、バックテスト結果、該当日付・台番一覧がそろっていて、Webアプリで照合できる条件だけです。

## 実装用の表記

条件名と条件式は、以下のように機械的に書いてください。

```text
条件名：
採用区分：通常採用 / 参考表示 / 見送り / 未採用
条件式：
期待値表示：
対象日数：
選択台数：
総G数：
BB：
RB：
BB確率：
RB確率：
合算確率：
平均差枚：
機械割：
勝率：
該当日付・台番一覧：
実装上の注意：
```

条件式は、文章ではなく、できるだけ以下のように書いてください。

```text
historyDays >= 21 && highContentCount3 >= 1 && rbRate7 >= 350 && diff14 <= -1000
```

条件式として数値化できないものは、実装候補ではなく参考仮説として扱ってください。

これは、あるパチスロ店における**特定1機種**の過去データをCSVにまとめたものです。

このCSVをもとに、指定した店舗がこの機種において高設定を入れる場所について、**設定師のクセや傾向**を分析してください。

目的は、翌日に高設定が入りやすい台を事前に予測し、狙い台を決めるための**「狙い度」100点満点ロジック**を作ることです。

ただし、最終的な成果物は100点満点ロジックだけで終わらせないでください。

このプロンプトでは、必ず以下の3種類を別々に作ってください。

1. **機種別100点満点ロジック**
    
    - 全台に点数が付く、実戦用の絶対評価ロジック
    - Webアプリの「機種別」列に入れる前提
    - 点数表、加点、減点、上限、危険条件を明確にする
2. **機種別の段階的な採用条件**
    
    - Webアプリの「条件」列に入れる前提
    - 通常機種では、期待機械割102%〜106%付近の条件を、できるだけ細かく段階的に作る
    - ただし、対象機種がネオアイムジャグラーEXまたはSアイムジャグラーEXの場合は、期待機械割ではなく期待RBを主軸に、1/310以下、1/300以下、1/290以下、1/280以下、1/270以下の段階で整理する
    - ネオアイムジャグラーEXとSアイムジャグラーEXは同じ評価基準を使うが、別機種として扱い、機種名や集計は統合しない
    - 対象機種名にマイジャグラーを含む場合も特例として扱い、期待機械割ではなく期待RBを主軸に、1/320以下、1/310以下、1/300以下、1/290以下、1/280以下の段階で整理する
    - 対象機種名にゴーゴージャグラーを含む場合も特例として扱い、期待機械割ではなく期待RBを主軸に、1/300以下、1/290以下、1/280以下、1/270以下、1/260以下の段階で整理する
    - 対象機種名にミスタージャグラーを含む場合も特例として扱い、期待機械割ではなく期待RBを主軸に、1/320以下、1/310以下、1/300以下、1/290以下、1/280以下の段階で整理する
    - 対象機種名にファンキージャグラーを含む場合も特例として扱い、期待機械割ではなく期待RBを主軸に、1/320以下、1/310以下、1/300以下、1/290以下、1/280以下の段階で整理する
    - 対象機種名にジャグラーガールズを含む場合も特例として扱い、期待機械割ではなく期待RBを主軸に、1/300以下、1/290以下、1/280以下、1/270以下、1/260以下の段階で整理する
    - 対象機種名にハッピージャグラーを含む場合も特例として扱い、期待機械割ではなく期待RBを主軸に、1/310以下、1/300以下、1/290以下、1/280以下、1/270以下の段階で整理する
    - 対象機種名にウルトラミラクルジャグラーを含む場合も特例として扱い、期待機械割ではなく期待RBを主軸に、1/330以下、1/320以下、1/310以下、1/300以下、1/290以下の段階で整理する
    - 広め条件、本命条件、強条件、最本命条件のように、座る価値の強弱が分かる形にする
    - 条件ごとに、対象日数、選択台数、合算、RB/REG、平均差枚、機械割を必ず出す
3. **自由度MAXの採用条件**
    
    - 100点満点ロジックや点数閾値に縛らず、最も実戦期待値が高い座り方を自由に再探索する
    - 単独条件、複合条件、見送り条件を自由に作ってよい
    - 機種別100点ロジックと違う結論になってもよい
    - 点数ロジックより優先してよい条件が見つかった場合は、必ず明記する

2と3は必ず分けてください。

2はWebアプリ上で、その台がどのくらい座る価値があるかを段階的に見せるための採用条件です。  
3は点数ロジックに縛らず、その店舗・その機種で最も強い座り方を見つけるための自由探索です。

# Webアプリ実装・照合のための厳密化ルール

この回答は、単なる分析レポートではなく、後でCodexがWebアプリへ実装し、Webアプリ上のバックテスト結果と照合するための仕様書として作ってください。

したがって、自然言語のクセ説明だけで終わらせず、Webアプリで再現できる条件式、集計期間、変数定義、該当台一覧を必ず出してください。

## 集計プロトコルを必ず明記する

回答内のバックテストごとに、以下を必ず明記してください。

- バックテストに使った実績日範囲
- Webアプリで入力すべき予測日基準の開始日・終了日
- 最新日として除外した日付
- 履歴計算に使い始めた最初の日付
- 台番変更、増台、減台、島変更がある場合の履歴リセット日
- 店休日、欠損日、全台G数0の日を営業日カウントに含めたか
- 通常日とイベント日を分けたか。分けない場合は理由
- 対象機種名を統合したか、分離したか
- Webアプリ側で機種名をどう指定すべきか
- Webアプリの「設定分布を表示」をONにするかOFFにするか

特に、バックテストの「実績日」と、Webアプリに入力する「予測日基準の日付」が1日ずれる可能性を必ず意識してください。

## Webアプリの設定分布表示は必要な時だけONにする

CodexがWebアプリでバックテスト照合する時は、原則として「設定分布を表示」はOFFで確認する前提にしてください。

まずは、選択台数、総G数、BB、RB、BB確率、RB確率、合算、差枚、平均差枚、機械割、勝率の一致を優先します。

ただし、回答内で平均設定、設定5・6推定率、設定4以上推定率、設定5以上推定率、設定分布を照合対象にしている条件では、最終確認時だけ「設定分布を表示」をONにしてください。

設定分布のON/OFFで選択台数、総G数、BB、RB、差枚、機械割が変わる場合は、表示切り替えではなく集計条件に問題がある可能性があります。その場合は、条件式、対象期間、履歴不足、日付ずれを確認してください。

## 変数定義を必ず表にする

点数表や採用条件で使う全ての指標について、以下の形式で定義表を作ってください。

| 指標名 | 計算式 | 使う履歴範囲 | 欠損・低G数の扱い | 未来情報を含まない理由 |
|---|---|---|---|---|

たとえば、`angle14`、`diff7`、`rb5`、`combined3`、`daysSince56`、`p56avg5`、`rank`、`topGap`、`dangerCount`、`boostCount` のような指標は、必ず計算式まで書いてください。

「沈み」「深い」「弱い」「本物感」「見せ場」「処遇完了」「近隣が強い」のような言葉だけで終わらせず、最終的に採用条件へ使うものは必ず数値条件へ変換してください。

数値条件へ変換できないものは、実装候補ではなく参考仮説として扱ってください。

## 採用条件は機械的な条件式で出す

Webアプリへ実装する採用条件は、必ず次のように書いてください。

```text
条件名：
条件式：
期待値表示：
対象日数：
選択台数：
該当日付・台番一覧：
実装可否：
実戦上の位置づけ：
```

条件式は、以下のような機械的に実装できる形にしてください。

```text
angle14 <= -90 && prevDiff <= -1000 && daysSince56 >= 8 && daysSince56 <= 28
```

バックテスト結果を出した条件式と、Codexに実装させる条件式を途中で変えないでください。

分析途中で別条件を試した場合は、最終的に実装する条件と、参考で試しただけの条件を明確に分けてください。

## 該当日付・台番一覧を必ず出す

Webアプリに実装してよい採用条件については、条件ごとに該当した全データを以下の形式で出してください。

| 条件名 | 予測日 | 実績日 | 台番 | score | rank | topGap | 差枚 | G数 | BB | RB |
|---|---|---|---:|---:|---:|---:|---:|---:|---:|---:|

この一覧は、CodexがWebアプリのバックテスト結果と突き合わせるための正解リストです。

件数が多い場合でも、Webアプリへ実装する最終採用条件については省略しないでください。

どうしても出力上限で全件を出せない場合は、その条件を「実装候補」ではなく「参考条件」として扱い、Webアプリでの再分析が必要であることを明記してください。

## 順位と次点差の定義を固定する

`rank`、`順位`、`topGap`、`次点差` を使う場合は、必ず以下を明記してください。

- 同一機種内だけで順位を付けたか
- 通常日、イベント日、全日共通のどの母集団で順位を付けたか
- 履歴不足台を順位母集団に含めたか
- 見送り条件に当たる台も順位母集団に含めたか
- 同点を同順位にしたか、並び順で別順位にしたか
- 次点差は同点を飛ばした次の点との差か、単純に次の行との差か
- 次点差がない単独台の日をどう扱ったか

これを明記できない順位条件や次点差条件は、Webアプリ実装候補にしないでください。

## 実装候補と参考条件を分ける

以下を全て満たすものだけを、Webアプリへ実装してよい条件として扱ってください。

- 条件式が機械的に書けている
- 変数定義が明記されている
- バックテスト結果が出ている
- 該当日付・台番一覧が出ている
- 件数が少なすぎる場合は注意書きがある

以下に当たるものは、実装候補ではなく参考条件として扱ってください。

- 条件式が曖昧
- 順位や次点差の定義が曖昧
- 該当日付・台番一覧がない
- 途中で条件式を変えていて、どの条件のバックテスト結果か分からない
- 件数が少なすぎて過剰最適化の疑いが強い

参考条件を、Webアプリの採用条件として実装する前提で書かないでください。

# 重要な前提

## 除外するデータ・列

- CSV内の**最新日の行**は、営業途中の未完成データである可能性があるため、必ず除外してください。
    
- 「狙い度」「狙度」「ブドウ」「ぶどう」」「次差」などの列が存在する場合、それらは**最終ロジックの説明変数として使わないでください**。
    
- ただし「設定」列が存在し、高設定判定の検証ラベルとして使う必要がある場合は、以下を必ず分けてください。
    
    - 設定列を使った参考検証
        
    - 設定列を使わない実戦用検証
        
- 最終的に採用する狙い度ロジックは、**実戦で当日前に分からない列を使わない形**にしてください。
    

## 未来情報の禁止

ある日を判定する場合、その日以前のデータだけを使って翌日を予測してください。

翌日のG数、翌日のBB、翌日のRB、翌日の差枚、翌日の設定など、実戦時点で分からない未来情報を、狙い度計算に使わないでください。

## 特定日・曜日の扱い

「特定日だから+◯点」「曜日が◯曜日だから+◯点」のように、日付や曜日そのものを狙い度の直接加点にしないでください。

特定日や曜日は、全台共通の期待感、客の期待、稼働量、回されやすさに影響し、結果として高内容に見えやすくなる可能性があります。

そのため、特定日・曜日は以下の扱いにしてください。

- 特定日別、通常日別、曜日別の成績差は確認してよい
- ただし、最終的な100点ロジックの点数項目には入れない
- 「特定日だから高設定を入れやすい」という前提で加点しない
- 「特定日だけ採用」「特定曜日だけ採用」のような条件を、最終採用条件の主軸にしない
- 特定日や曜日で成績が良く見える場合は、稼働が増えて高設定っぽい台が見えやすいだけではないかを必ず疑う

最終ロジックでは、日付や曜日そのものではなく、台ごとの直近履歴、沈み、返済未完了、処遇完了、ボーナス内容、G数信頼度など、実戦で台選びに使える要素を優先してください。

## 通常日式・イベント日式を分けるかの判断

CSVに `特定日` 列が存在する場合は、全日共通ロジックを作ったうえで、通常営業日とイベント日で設定の入れ方のクセが明確に違うかを必ず検証してください。

`特定日` 列の扱いは以下の通りです。

- `特定日` が `はい` の行をイベント日として扱う
- `特定日` が `いいえ` の行を通常営業日として扱う
- `3の付く日`、`6の付く日`、`末尾0の日`、曜日など、CSV外の固定日付ルールを推測して使わない
- 店舗ごとのイベント日は、必ずCSVの `特定日` 列を正とする

まず、全日共通で以下を作ってください。

1. 全日共通の100点満点ロジック
2. 全日共通の段階的採用条件
3. 全日共通の自由度MAX採用条件

そのうえで、通常営業日とイベント日で、以下に明確な違いがあるかを比較してください。

- 高内容台が入る前の履歴パターン
- 連敗、沈み、返済未完了、処遇完了の効き方
- 前回高内容からの間隔
- 前日高内容の据え置き、不発据え置き、出た後の扱い
- 近隣や同機種内順位の効き方
- ボーナス内容、G数信頼度、低稼働の扱い
- 採用条件のバックテスト結果

通常営業日とイベント日でクセが明確に違い、かつ件数が少なすぎず再現性がある場合は、全日共通ロジックとは別に、以下も追加で作ってください。

1. 通常日専用の100点満点ロジック
2. 通常日専用の段階的採用条件
3. 通常日専用の自由度MAX採用条件
4. イベント日専用の100点満点ロジック
5. イベント日専用の段階的採用条件
6. イベント日専用の自由度MAX採用条件

この場合でも、全日共通ロジックは破棄しないでください。

Webアプリでは、全日共通ロジックを `機種別` 列に表示し、狙い対象日が通常営業日なら `通常日` 列、イベント日なら `特定日` 列に専用ロジックを表示する想定です。

したがって、回答では以下のように役割を分けてください。

- `全日共通ロジック`：日付種別に依存しない土台のクセを見るためのロジック
- `通常日専用ロジック`：通常営業日にだけ使う補助ロジック
- `イベント日専用ロジック`：イベント日にだけ使う補助ロジック

実戦上は、`機種別` 列と `通常日` または `特定日` 列の両方が強い台をより高く評価します。

一方で、通常営業日とイベント日でクセの違いが弱い場合、または件数不足で専用ロジックが過剰最適化になりそうな場合は、通常日専用ロジックとイベント日専用ロジックは作らず、全日共通ロジックだけを提出してください。

その場合も、なぜ分けない方がよいのかを短く説明してください。

なお、通常日専用ロジックやイベント日専用ロジックを作る場合でも、点数項目に `特定日だから加点` のような項目を入れてはいけません。

通常日・イベント日で母集団を分けたうえで、その中の台ごとの履歴差、沈み、返済未完了、処遇完了、ボーナス内容、G数信頼度などを使ってロジックを作ってください。

## 台番変更・設置変更時の履歴の扱い

履歴は、原則として**台番単位**で追ってください。

途中で台番構成が変わっている場合や、同じ機種が別の台番群に移動している場合でも、旧台番と新台番を**設置順、並び順、島内ポジションで同一台としてつながないでください**。

たとえば、前半期間に `1078番台〜1102番台`、後半期間に `873番台〜887番台` がある場合、

```text
旧台番群の1番目 = 新台番群の1番目
```

のように見なしてはいけません。

この場合は、以下のように扱ってください。

- 旧台番期間の履歴は、旧台番期間内だけで使う
- 新台番期間の履歴は、新台番期間内だけで使う
- 台番変更日をまたいで、直近3日、5日、7日、14日、21日などの履歴をつなげない
- 前回高内容からの日数、連敗数、沈み滞在、返済未完了、処遇完了なども、台番変更時点でリセットする
- 台番変更直後は履歴が足りないため、必要な履歴日数がたまるまではバックテスト対象から除外するか、低信頼扱いにする

並び順や設置順は、近隣台、同じ島、左右の見せ場などの**当日または同一期間内の周辺状況**を見るためには使っても構いません。

ただし、台番変更前後の自台履歴をつなぐ目的では絶対に使わないでください。

もし「台番で追うべきか」「並び順で追うべきか」で迷う場合は、最終ロジックでは必ず台番ベースを優先してください。並び順ベースの検証を行う場合は、参考検証として分けて書き、最終採用条件には混ぜないでください。

# ロジック作成の基本方針

## 100点満点の絶対評価を作る

狙い度ロジックは、基本的に**絶対評価**を前提にしてください。

たとえば、

- 直近◯日の差枚が◯枚以下なら加点
    
- 直近◯日の合計G数が一定以上なら加点
    
- 直近◯日のボーナス内容が弱ければ加点
    
- 前回高内容から一定期間空いていれば加点
    

のように、どの台にも同じ基準で点数が付く形にしてください。

「その日の中で一番凹んでいるから+◯点」のような、相対評価だけに頼るロジックは避けてください。

## 固定台番・固定機種名の優遇は禁止

「855番だから+5点」のような固定台番優遇は避けてください。

もし特定台番が優遇されているように見える場合でも、以下のように、他の台や他機種にも応用できる思想に変換してください。

- 過去◯日間で高内容が◯回以上ある台
    
- 長期間高設定が入っていない台
    
- 前回高内容から◯営業日空いている台
    
- 直近で見せ場が少ない台
    
- 直近で処遇完了していない台
    

また、このCSVは1機種分のデータですが、「この機種だから+◯点」という機種名そのものへの固定加点もしないでください。

---

# 閾値は決め打ちしないこと

このプロンプトでは、特定の数字をこちらから指定しません。

たとえば、

- 何枚以上出たら「大きく出た」と扱うのか
    
- 何連敗から店が意識しているのか
    
- 何日間沈んでいたら「滞在」と見るのか
    
- 何G以上あればデータとして信頼するのか
    
- 何日間の累計差枚を見るべきなのか
    
- どの程度のRB率や合算確率を高内容と見るのか
    
- どの程度の次点差があれば単独候補として強いのか
    

これらは、こちらで固定せず、**CSVデータからあなた自身が探索してください**。

探索する際は、以下のような考え方を使ってください。

- 複数の期間を比較する
    
- 複数の閾値を比較する
    
- 分位点やデータ分布から候補を作る
    
- 前半/後半で再現性を確認する
    
- 件数が少なすぎる条件は過剰最適化として警戒する
    
- 成績が良くても、理屈が弱い条件は慎重に扱う
    

過去データに合わせすぎないように注意してください。

単に過去の成績が良くなる条件を後付けで増やすのではなく、再現性がありそうかを必ず確認してください。

# 高内容日の定義

まず、CSVの列構造を確認したうえで、**高設定っぽい日、または高内容日**を定義してください。

Aタイプ・ジャグラー系・ハナハナ系・ハナビ系・サンダー系のように、ボーナス内容が重要な機種では、以下を重視してください。

- ボーナス確率
    
- 特にRB率
    
- ボーナス合成確率
    
- 総G数
    
- BB/RBのバランス
    
- 差枚
    

ただし、RB率だけで判断しないでください。

**ボーナス確率が大事で、その中でも特にRB/REG確率が大事**という考え方で、高内容日を定義してください。

この系統の機種では、評価の優先順を必ず **RB/REG確率 ＞ ボーナス合成確率 ＞ 機械割** にしてください。

目標の機械割を達成するために、ボーナス合成確率やRB/REG確率を犠牲にする条件は採用しないでください。

また、設定列が存在する場合は、

- 設定列を使った高設定判定
    
- 設定列を使わない高内容判定
    

を分けて検証してください。

# 分析の基本手順

以下の順番で分析してください。

1. CSVの列構造を確認する
    
2. 日付、台番、G数、BB、RB、合成確率、差枚、機械割など、利用できる列を整理する
    
3. 除外すべき行・列を除外する

    - 台番構成が途中で変わっていないかを必ず確認する
        
    - 台番変更がある場合は、旧台番期間と新台番期間を分け、履歴をまたがせない
        
    - 台番変更直後の履歴不足期間を、何日分除外したか明記する
    
4. 高設定っぽい日、または高内容日を定義する
    
5. 高内容だった台の前日以前の特徴を洗い出す
    
6. その特徴を全データに当てはめたときに、期待値のある座り方になっているかを検証する
    
7. 100点満点の狙い度ロジックを作る
    
8. メインロジックとは別に、サブ条件・危険条件・見送り条件を作る
    
9. Webアプリに入れる前提で、通常機種は期待機械割102%〜106%付近、ネオアイムジャグラーEXとSアイムジャグラーEXは期待RB 1/310以下〜1/270以下、マイジャグラーを含む機種は期待RB 1/320以下〜1/280以下、ゴーゴージャグラーを含む機種は期待RB 1/300以下〜1/260以下、ミスタージャグラーを含む機種は期待RB 1/320以下〜1/280以下、ファンキージャグラーを含む機種は期待RB 1/320以下〜1/280以下、ジャグラーガールズを含む機種は期待RB 1/300以下〜1/260以下、ハッピージャグラーを含む機種は期待RB 1/310以下〜1/270以下、ウルトラミラクルジャグラーを含む機種は期待RB 1/330以下〜1/290以下の段階的な採用条件を作る
    
10. 点数ロジックに縛らない自由度MAXの採用条件を再探索する
    
11. 次点差によるフィルタリングを検証する
    
12. バックテスト結果を出す
    
13. 実戦でどう使うべきかをまとめる

# 設定師のクセとして検証してほしい典型パターン

以下は、設定師のクセとして考えられる典型例です。

ただし、これらに無理に当てはめる必要はありません。

データ上で弱いものは不採用にしてください。

## ローテーション系

### ローテーションで入れる店

直近で高設定を入れていない台に、順番に高設定を入れるパターン。

前回高内容からの日数、直近の高内容回数、一定期間内の投入間隔などを検証してください。

### ずっと高設定を入れない台がある店

ローテーション狙いをする客心理の逆をついて、同じ台に長期間高設定を入れないパターン。

長期間空いていることがプラスなのか、むしろ放置台としてマイナスなのかを検証してください。

---

## ヘコみ・上げ狙い系

### ヘコみに入れる店

直近の差枚が悪い台に高設定を入れるパターン。

前日だけを見るのではなく、複数の期間で検証してください。

どの期間の凹みを店が意識していそうか、データから探索してください。

### ヘコみに入れない店

ヘコみ台狙いをする客心理の逆をついて、凹み台に入れる確率が低いパターン。

凹みが深すぎる台、稼働が少なすぎる台、長期間沈みっぱなしの台が本当に狙えるのかを検証してください。

### よく出ている台に入れる店

ヘコみ狙いの逆をついて、直近で出ている台に入れるパターン。

ただし、単に出た台を据えるのか、それとも「まだ処遇完了していない出方」の台だけを使うのかを分けて検証してください。

---

## 連続投入・据え置き系

### 連続で同じ台に入れる店

同じ台に高設定を連続投入するパターン。

ただし、連続投入が何回まで有効なのかは決め打ちしないでください。

データから、

- 連続投入されやすい条件
    
- 連続投入されにくくなる条件
    
- 何回目以降に弱くなるか
    
- 不発後と大きく出た後で違いがあるか
    

を探索してください。

### 前日高設定で不発の台を据え置く店

高設定っぽい内容なのに差枚が伸びなかった台を、翌日もう一度使うパターン。

ただし、「不発」の定義は固定せず、ボーナス内容、差枚、G数、合成確率、RB率などから探索してください。

### 前日高設定でしっかり出た台を据え置く店

不発据え置き狙いの逆をついて、しっかり出た高設定台を翌日も使うパターン。

ただし、何枚以上出たら据え置きにくいのか、あるいはどの程度出ても据え置くのかは、データから探索してください。

---

## 稼働・見え方系

### 稼働が多い台を優遇する店

直近のG数が多い台、つまり客に見られている台に高設定を入れるパターン。

どの期間のG数が効いているか、どの程度のG数が必要かをデータから探索してください。

### 稼働が少ない台を優遇する店

あまり回されていない台に高設定を入れるパターン。

ただし、低稼働すぎる台はデータとして信頼できない可能性があります。

低稼働がプラスなのか、放置のサインなのかを分けて検証してください。

### 当たり回数が少ない台を返す店

直近でBB/RBなどのボーナス回数が少なく、客から見て印象が悪い台に高設定を入れるパターン。

ただし、当たり回数だけでなく、G数に対するボーナス確率として評価してください。

---

# 追加で検証してほしい重要観点

ここから先は、特に深掘りしてほしい追加観点です。

ただし、ここでも具体的な閾値は決め打ちせず、CSVデータから探索してください。

## 沈み滞在

直近の一定期間における合計差枚が、一定ライン以下の状態にどれくらい滞在しているかを見てください。

単に前日負けた台ではなく、一定期間ずっと返されていない台を店が返す可能性があります。

検証してほしいことは以下です。

- どの期間の合計差枚が効いているか
    
- どの程度沈んだ状態が効いているか
    
- 何日間その状態に滞在すると強くなるか
    
- 長く沈みすぎると逆に弱くなるか
    
- 沈み滞在はメイン点数に入れるべきか、サブ条件にするべきか
    

## 差枚の角度

単純な差枚マイナスではなく、G数に対してどれくらい急角度で沈んでいるかを見てください。

たとえば、一定期間の合計差枚を同期間の合計G数で割るような考え方です。

検証してほしいことは以下です。

- どの期間の角度が効いているか
    
- 急角度の沈みが強いのか
    
- 緩やかな沈みが強いのか
    
- G数が少ないだけのマイナスをどう扱うべきか
    
- 角度はメイン点数に入れるべきか、サブ条件にするべきか
    

## 返済未完了

一度出た後でも、過去の負けを返し切っていない台をもう一度使うパターンを検証してください。

単に「出たから終わり」ではなく、一定期間の累計差枚で見たときに、まだ未処遇と見なされる台があるかを確認してください。

検証してほしいことは以下です。

- どの期間の累計差枚で見るべきか
    
- 出た後でも再投入される台の共通点は何か
    
- ボーナス内容が強い台ほど再投入されやすいか
    
- 出玉だけ強い台と、ボーナス内容まで強い台で違いがあるか
    

## 処遇完了

直近で十分に出た台、見せ場を作り切った台、累計差枚が大きく戻った台を、店が「もう返した台」とみなして外すパターンを検証してください。

検証してほしいことは以下です。

- どの程度出ると処遇完了と見なされやすいか
    
- 何日間の累計差枚が戻ると弱くなるか
    
- 高内容で出た台と、内容は弱いが出ただけの台で違いがあるか
    
- 処遇完了は減点にするべきか、見送り条件にするべきか
    

## 大きく出た翌日の扱い

高内容かつ大きく出た台を翌日も使う場合と、使わない場合の違いを検証してください。

ただし、何枚以上を「大きく出た」と見るかは決め打ちしないでください。

データから、どの出玉帯を境に挙動が変わるのかを探索してください。

検証してほしいことは以下です。

- どの程度出ると翌日弱くなるか
    
- どの程度出ても翌日残るパターンがあるか
    
- 出た日のRB率や合算確率が強い場合は残りやすいか
    
- 出る前の凹みや連敗が残っている場合は残りやすいか
    
- 出た後の累計差枚がまだ弱い場合は残りやすいか
    
- 前日以前に見せ場があった台は落ちやすいか
    

## ボーナス内容の本物感

Aタイプ・ジャグラー系では、出玉だけでなくボーナス内容を重視してください。

特に、以下を分けて見てください。

- RB率が強い台
    
- 合算確率が強い台
    
- BBに寄って出ただけの台
    
- RBは強いが差枚が伸びなかった台
    
- 合算もRBも強い台
    
- G数が少なくて判断しにくい台
    

RB率だけでなく、合算確率も必ず見てください。

## 連敗数

現在連敗数が設定投入に関係しているかを検証してください。

ただし、具体的な連敗数はこちらから指定しません。

どの連敗数から強くなるのか、どの連敗数で弱くなるのか、データから探索してください。

検証してほしいことは以下です。

- 連敗数は多いほど強いのか
    
- 特定の連敗数にピークがあるのか
    
- 長期連敗は放置台になっていないか
    
- 稼働量によって連敗数の意味が変わるか
    
- 連敗数はメイン点数に入れるべきか、サブ条件にするべきか
    

## 最低限のG数

凹み、連敗、不発、RB内容などの条件があっても、G数が少なすぎる場合は信頼度が低い可能性があります。

どの程度のG数があれば、前日以前のデータとして信頼できるのかを探索してください。

検証してほしいことは以下です。

- 前日G数の最低ライン
    
- 直近複数日合計G数の最低ライン
    
- 低G数の凹みは使えるのか
    
- 高G数で凹んだ台の方が強いのか
    
- 高G数で出た台は処遇完了になりやすいのか
    

## 列・近隣台・島の見せ場

同じ列、近い台番、同じ島で最近どれだけ見せ場があったかによって、投入位置が変わる可能性があります。

ただし、固定台番優遇にならないようにしてください。

あくまで、

- 近隣台の直近状況
    
- 同じ列の直近高内容回数
    
- 近い台番で見せ場が出た後かどうか
    
- 周辺が出ている中で取り残されている台かどうか
    

のように、汎用的な形で検証してください。

# 完成させるロジック

最終的に、以下の3系統を必ず分けて作ってください。

## 1. 機種別100点満点ロジック

100点満点の絶対評価スコアを作ってください。

条件ごとの点数、計算式、上限、下限を明確にしてください。

各台に対して、当日前に分かる情報だけで点数が付く形にしてください。

このロジックは、Webアプリの「機種別」列に表示する点数として使う前提です。

以下を必ず書いてください。

- 点数表
    
- 加点条件
    
- 減点条件
    
- 上限と下限
    
- 履歴不足時の扱い
    
- どの要素を重視したロジックなのか
    

## 2. サブ条件・信頼度判定

メイン狙い度とは別に、信頼度を上下させるサブ条件を作ってください。

サブ条件は、メイン点数に無理に全部混ぜ込まないでください。

特に、連敗数や差枚など、メインロジックと同じ情報を二重評価しないように注意してください。

サブ条件は以下のように整理してください。

### 強化条件

狙い度の信頼度を上げる条件。

例：

- 沈み滞在が強い
    
- 差枚の角度が強い
    
- 返済未完了感がある
    
- ボーナス内容に本物感がある
    
- G数の信頼度が高い
    

### 危険条件

狙い度が高くても注意すべき条件。

例：

- 処遇完了の可能性が高い
    
- 低稼働すぎて判断しにくい
    
- 長期放置台の可能性がある
    
- 出玉だけ強く、ボーナス内容が弱い
    
- 直近で見せ場を作り切っている
    

### 見送り条件

狙い度が高くても、その日は見送った方がよい条件。

例：

- 強化条件が少ない
    
- 危険条件が多い
    
- G数が少なすぎる
    
- 処遇完了の可能性が高い
    
- 過去データ上、同条件の再現性が弱い
    

## 3. Webアプリ用の段階的な採用条件

Webアプリの「条件」列に入れるための採用条件を作ってください。

## 4. 自由度MAXの採用条件

100点満点ロジック、点数閾値、次点差、既存の採用条件に縛らず、自由に条件を再探索してください。

目的は、点数ロジックでは拾いきれない「この店舗・この機種で本当に強い座り方」を見つけることです。

この自由探索では、以下を優先してください。

- Aタイプ、ジャグラー系、ハナハナ系、ハナビ系、サンダー系では、RB/REG確率を最優先
    
- 次に合算確率
    
- 最後に機械割
    
- スマスロ系、沖ドキ系などでは、機械割と平均差枚、勝率、件数のバランス
    

自由探索では、以下のような形を自由に探してください。

- 単独で強い条件
    
- 複数条件が重なった時だけ強い条件
    
- 100点ロジックでは高くないが、実績が強い条件
    
- 高スコアでも避けるべき見送り条件
    
- 打つ日を増やすための妥協条件
    
- 本命条件がない日の代替条件
    

自由探索で見つけた条件は、以下の表で出してください。

- 条件名
    
- 条件式
    
- 対象日数
    
- 選択台数
    
- RB/REG確率
    
- 合算確率
    
- 平均差枚
    
- 機械割
    
- 100点満点ロジックとの関係
    
- 実戦で点数ロジックより優先すべきか
    

自由探索の結論が100点満点ロジックと違う場合は、その違いを明確に説明してください。

たとえば、

- 点数ロジックは毎日の順位付けに向いている
    
- 自由探索条件は、条件が出た日だけ打つ本命ルールに向いている
    
- 段階的採用条件は、Webアプリ上で価値の強弱を見るために向いている
    

のように、用途を分けて整理してください。

# 次点差フィルタリング

完成したメイン狙い度ロジックについて、**次点差**によるフィルタリングも必ず検証してください。

次点差とは、日ごとの狙い度1位と2位の点差のことです。

たとえば、毎日1位の台を選ぶ場合に、

- 次点差なし
    
- 1位と2位の点差が一定以上の日だけ座る
    
- 点差が大きい日だけ座る
    
- 点差が小さい日は見送る
    

といった検証をしてください。

ただし、何点差以上が良いかはこちらで指定しません。

データから、どの程度の点差があると成績が改善するのかを探索してください。

# バックテストで必ず出すもの

最低限、以下を検証してください。

## 毎日座る系

1. 日ごとに狙い度第1位の台に毎日座り続けた場合
    
2. 日ごとに狙い度第1位〜第◯位の台に毎日座り続けた場合
    

第何位までを見るべきかは、データから判断してください。

広範囲にすることでチャンスは増えますが、結果を犠牲にしすぎないことを優先してください。

## 点数閾値系

狙い度が一定以上の台に座り続けた場合を検証してください。

どの点数以上を閾値にするかは、データから複数パターン探索してください。

## 次点差系

狙い度1位の台について、2位との点差でフィルタリングした場合を検証してください。

どの点差以上で成績が改善するかを、複数パターンで比較してください。

## サブ条件系

メイン狙い度に加えて、サブ条件が重なる日だけ打った場合を検証してください。

例：

- 狙い度上位かつ沈み滞在が強い
    
- 狙い度上位かつ角度が強い
    
- 狙い度上位かつ返済未完了感がある
    
- 狙い度上位かつボーナス内容に本物感がある
    
- 狙い度上位かつ危険条件が少ない
    

ただし、具体的にどの組み合わせが良いかは、データから探索してください。

## 見送り系

狙い度は高いが危険条件がある日を除外した場合を検証してください。

毎日必ず打つ検証と、条件が揃った日だけ打つ検証を分けてください。

## Webアプリ用の段階的採用条件系

Webアプリの「条件」列に入れる前提で、段階的な採用条件を検証してください。

以下のように、期待値の強弱が分かるようにしてください。

- 102%台の広め条件
    
- 103%台の弱め本命
    
- 104%台の本命条件
    
- 105%台の強条件
    
- 106%前後の最本命条件
    

点数閾値、順位、次点差、強化条件、危険条件除外、単独特徴を組み合わせて構いません。

ただし、すべてを無理に104%以上へ寄せる必要はありません。

狙い度ランキングで「広く拾うならこの程度」「本命だけならこの程度」と分かることを重視してください。

## 自由度MAX探索系

100点満点ロジックをいったん無視し、RB/REG、合算、機械割、平均差枚、勝率、件数のバランスだけで自由に探索した条件も必ず検証してください。

この検証では、以下を分けてください。

- 最もRB/REGが軽くなる条件
    
- 機械割が最も高くなる条件
    
- 件数と成績のバランスがよい条件
    
- 打てる日を増やすための妥協条件
    
- 見送りにした方がよい条件
    

自由探索条件が100点満点ロジックや段階的採用条件より強い場合は、実戦ではどちらを優先すべきかを必ず書いてください。

# ネオアイムジャグラーEXまたはSアイムジャグラーEXの場合の特例

提供されたCSVの対象機種が `ネオアイムジャグラーEX` または `SアイムジャグラーEX` の場合は、この特例を通常ルールより優先してください。

ネオアイムジャグラーEXとSアイムジャグラーEXは同じ評価基準を使いますが、別機種として扱ってください。
同じ店舗に両方が存在する場合でも、機種名や集計を統合せず、CSVに含まれる対象機種だけで分析してください。

ネオアイムジャグラーEXまたはSアイムジャグラーEXでは、**設定5・6級の台に座ることだけを成功**とみなしてください。

設定5と設定6の区別は重視しないでください。  
理由は、実戦データから設定5と設定6を明確に分けることが困難であり、さらに多くの店舗では設定6をほとんど使わず、設定5が実質上限であることが多いためです。

この分析では、設定5・6級に座れた割合を最重要指標にしてください。

設定4以下に座ることは、今回の目的では**失敗扱い**にしてください。  
設定4は理論上の機械割では設定1より高いですが、この特例の狙い台ロジックでは成功に含めないでください。

したがって、平均機械割が102%前後出ていても、設定5・6推定率が低い条件や、設定4以下を多く含む可能性が高い条件は、採用条件として扱わないでください。
逆に、平均機械割や平均RBが多少劣っても、設定5・6推定率が高く、設定4以下推定率が低い条件は高く評価してください。

ネオアイムジャグラーEXとSアイムジャグラーEXの設定別ボーナス確率は以下です。

| 設定 | BIG確率 | REG確率 | 合成確率 |
|---|---:|---:|---:|
| 設定1 | 1/273.1 | 1/439.8 | 1/168.48 |
| 設定2 | 1/269.7 | 1/399.6 | 1/161.02 |
| 設定3 | 1/269.7 | 1/331.0 | 1/148.61 |
| 設定4 | 1/259.0 | 1/315.1 | 1/142.15 |
| 設定5 | 1/259.0 | 1/255.0 | 1/128.49 |
| 設定6 | 1/255.0 | 1/255.0 | 1/127.50 |

この特例ではREG確率の設定差が最も大きいですが、単純な平均RBや固定しきい値だけで評価しないでください。
必ず以下の方法で、各台ごとの設定1〜6推定率を計算してください。

## 設定推定率の計算方法

各台について、総G数を `G`、BIG回数を `B`、REG回数を `R` とします。

各設定について、その設定のBIG確率を `pB`、REG確率を `pR` とします。

各設定の重みは、以下で計算してください。

```text
設定ごとの重み =
組み合わせ(G, B) × pB^B × (1 - pB)^(G - B)
×
組み合わせ(G, R) × pR^R × (1 - pR)^(G - R)
```

上記は数値が非常に小さくなりやすいため、可能であれば対数で計算してください。

```text
設定ごとの対数重み =
log(組み合わせ(G, B)) + B × log(pB) + (G - B) × log(1 - pB)
+
log(組み合わせ(G, R)) + R × log(pR) + (G - R) × log(1 - pR)
```

設定1〜6の対数重みを出したら、最大の対数重みを引いてから指数に戻し、合計が100%になるように正規化してください。

```text
補正後重み = exp(その設定の対数重み - 最大の対数重み)
設定ごとの推定率 = その設定の補正後重み ÷ 全設定の補正後重み合計
```

最重要指標は以下です。

```text
設定5・6推定率 = 設定5推定率 + 設定6推定率
設定4以下推定率 = 設定1推定率 + 設定2推定率 + 設定3推定率 + 設定4推定率
```

設定5と設定6を分けて評価する必要はありません。
設定5・6推定率を、この特例における「56に座るヒット率」の代理指標として扱ってください。

合成確率は確認用として必ず併記してください。
ただし、BIGとREGを別々に使って設定推定率を出しているため、同じ情報を二重に評価しないよう、合成確率を主計算に重ねて入れないでください。

## ネオアイムジャグラーEXまたはSアイムジャグラーEXの採用条件を作る基準

採用条件は、平均RBが軽くなる条件ではなく、設定5・6推定率が高い台を多く選び、設定4以下推定率が高い台を避けられる条件として作ってください。

Webアプリ用の段階的採用条件では、ネオアイムジャグラーEXまたはSアイムジャグラーEXだけ期待機械割ではなく期待RBで段階を分けてください。
段階は、期待RB 1/310以下、1/300以下、1/290以下、1/280以下、1/270以下を目安にしてください。  
ただし、段階名や色分けの根拠は期待RBに置きつつ、採用判断そのものは設定5・6推定率を最重視し、設定4以下推定率が高い条件は上位段階に置かないでください。

各条件では、最低限以下を比較してください。

- 平均 設定5・6推定率
    
- 中央値 設定5・6推定率
    
- 設定5・6推定率 70%以上の割合
    
- 設定5・6推定率 50%以上の割合
    
- 設定5・6推定率 30%未満の割合
    
- 設定4以下推定率 70%以上の割合
    
- RB 1/300以下の割合
    
- RB 1/400超の割合
    
- 合成 1/130以下の割合
    
- 合成 1/140以下の割合
    
- 平均RBと中央値RB
    
- 平均合成と中央値合成

RB 1/270以下だけを成功扱いしないでください。
RB 1/300前後でも、BIG回数や合成確率との兼ね合いで設定5・6推定率が高ければ、十分に評価対象へ含めてください。

Codex貼り付け用 実装依頼では、検証方法の中に次の実装完了条件を必ず強調して入れてください。

- Webアプリ上で実際にバックテストを回し、回答内に書いた採用条件ごとの選択台数、総G数、BB確率、RB/REG、合算、平均差枚、機械割と照合する
- Webアプリ側のバックテスト結果と回答内のバックテスト結果が、実用上許容できる範囲まで一致しない限り、実装完了扱いにしない
- ここでいう許容範囲は、選択台数、総G数、BB数、RB数などの母数がほぼ一致し、確率、機械割、平均差枚の差が丸め誤差や表示単位差で説明できる程度とする
- 回答内では整合しているのにWebアプリで一致しない場合は、条件式、最新日除外、未来情報除外、対象機種名、台番、履歴計算、通常日/イベント日の分岐、集計期間の違いを疑い、Webアプリ上で再検証しながら修正する
- ただし、同じ条件について主要なズレ原因を3つ確認しても一致しない場合、または30分以上かかる場合は、通常採用として有効化せず、未採用理由を照合ログに記録する
- 回答内の条件式、該当日付・台番一覧、集計表が最初から矛盾している条件は、Webアプリ側で無理に補正して合わせない
- 採用条件のラベル名や期待値表示だけを写して終わらせず、実際にWebアプリのバックテストで再現できる条件式に落とし込む
- 該当日付・台番一覧がある場合は、Webアプリの該当台と1件ずつ突き合わせる
- 順位、次点差、近隣、履歴不足の定義が曖昧な条件は、ラベルだけ実装せず参考条件として扱う
- Webアプリで回答値を再現できない条件は、通常採用条件として残さず、未採用理由を照合ログに記録する
- Webアプリ照合では、最初から全条件で設定分布を表示しない。原則OFFで主要成績を合わせ、設定推定率や設定分布が必要な条件だけ最終確認時にONにする

特に、採用条件はWebアプリへ移しやすいように、以下の形式で書いてください。

```text
条件名：
条件式：
期待値表示：
該当日付・台番一覧：
実装可否：
実戦上の位置づけ：
```
