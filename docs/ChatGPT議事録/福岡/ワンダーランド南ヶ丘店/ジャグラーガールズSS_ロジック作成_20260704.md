以下、CSV実データだけで作った **ワンダーランド南ヶ丘店 / ジャグラーガールズSS** 用の狙い台ロジックです。
今回の回答は分析レポートではなく、あとでCodexがWebアプリへ実装できる「実装用の正本」を最後に固定する、というアップロード済みプロンプトの前提に合わせています。 また、最新日の行は未完成データの可能性があるため除外する指定に従い、CSV最新日の **2026-07-03** は分析から外しました。 ジャグラーガールズ系は期待機械割ではなく、期待RB 1/300、1/290、1/280、1/270、1/260 の段階で整理し、合算1/130以下も確認ラインとして扱う指定を優先しています。

## 結論

この機種は、**直近でボーナス合算が重く見えている台を、数日〜2週間後に返す傾向**が最も使えます。逆に、直近7日〜14日でしっかり出た台はかなり弱く、処遇完了として減点・見送り寄りにした方がよいです。

通常採用は以下の3条件です。

| 優先 | 条件名                    | 採用   |     実績RB |       合算 |     平均差枚 |     機械割 | 位置づけ       |
| -: | ---------------------- | ---- | -------: | -------: | -------: | ------: | ---------- |
|  1 | ガールズ赤_青＋前日1000G＋7日REG重 | 通常採用 | 1/267.02 | 1/121.74 | +811.94枚 | 108.13% | 件数少なめだが最優先 |

|  3 | ガールズ青_7日重合算＋14日高内容1回以下 | 通常採用 | 1/297.38 | 1/135.00 | +336.64枚 | 103.48% | 広め入口       |

`ガールズ緑_5日重合算＋14日REG重＋7日沈み角度` と `自由MAX_長期REG重＋7日角度沈み` は、全体数値は強いですが前半/後半のブレが大きいため、通常採用ではなく **参考表示** に落とします。

## 2. 高内容日の定義

ジャグラーガールズSSは、評価優先順を **RB/REG確率 ＞ 合算確率 ＞ 設定5・6推定率の分布 ＞ 機械割 ＞ 平均差枚** としました。対象機種では設定5以上を成功目標にし、設定5・6推定率を主指標、設定4以下推定率を失敗リスクとして扱う指定に合わせています。

| ラベル  | 定義                                                                                        |
| ---- | ----------------------------------------------------------------------------------------- |
| 準高内容 | `G数 >= 2500 && p56 >= 0.30 && 合成分母 <= 145` または `G数 >= 2000 && RB分母 <= 330 && 合成分母 <= 140` |
| 高内容  | `G数 >= 3000 && p56 >= 0.40 && 合成分母 <= 135` または `G数 >= 2500 && RB分母 <= 300 && 合成分母 <= 130` |
| 強高内容 | `G数 >= 3000 && p56 >= 0.55 && RB分母 <= 270 && 合成分母 <= 125`                                 |

`p56` は、実績日のG数・BB・RBから設定1〜6の尤度を出し、設定5推定率＋設定6推定率として計算しました。これは検証ラベルであり、当日朝の予測説明変数には使いません。履歴上の過去日については、前日以前に確定しているデータなので使用可としました。

# 実装時の優先順位
1. まず全台に100点満点scoreを表示する。
2. 条件列には通常採用の青・黄・赤だけを主表示する。
3. 緑と自由MAXは参考表示に留め、通常採用条件より優先しない。
4. 紫は実装しない。
5. rank/topGap単独条件は実装しない。
6. diff14>=3000、diff7>=2500は危険減点・見送り警告として使う。

# 既存条件の扱い
対象店舗・対象機種に既存のジャグラーガールズSS条件がある場合、この正本の青・黄・赤を主条件として置き換える。
ただし、既存の汎用表示や説明文は必要に応じて残してよい。
緑・自由MAXは通常採用ではなく参考条件としてだけ表示する。

# Webアプリ上の表示先
全日共通ロジックを「機種別」列に表示する。
通常日列・特定日列には専用ロジックを作らない。
条件列には、青・黄・赤の段階条件を表示する。
参考条件として緑・自由MAXを表示できる場合は、通常採用とは別ラベルにする。

# 検証方法
Webアプリ上で実際にバックテストを回し、回答内に書いた採用条件ごとの選択台数、総G数、BB数、RB数、BB確率、RB/REG、合算、平均差枚、機械割、勝率と照合する。
Webアプリ側のバックテスト結果と回答内のバックテスト結果が、実用上許容できる範囲まで一致しない限り、実装完了扱いにしない。
許容範囲は、選択台数、総G数、BB数、RB数などの母数がほぼ一致し、確率、機械割、平均差枚の差が丸め誤差や表示単位差で説明できる程度とする。
回答内では整合しているのにWebアプリで一致しない場合は、条件式、最新日除外、未来情報除外、対象機種名、台番、履歴計算、通常日/イベント日の分岐、集計期間の違いを疑い、Webアプリ上で再検証しながら修正する。
ただし、同じ条件について主要なズレ原因を3つ確認しても一致しない場合、または30分以上かかる場合は、通常採用として有効化せず、未採用理由を照合ログに記録する。
採用条件のラベル名や期待値表示だけを写して終わらせず、実際にWebアプリのバックテストで再現できる条件式に落とし込む。
該当日付・台番一覧とWebアプリの該当台を1件ずつ突き合わせる。
順位、次点差、近隣、履歴不足の定義が曖昧な条件は、ラベルだけ実装せず参考条件として扱う。
Webアプリで回答値を再現できない条件は、通常採用条件として残さず、未採用理由を照合ログに記録する。
設定分布表示は原則OFFで主要成績を合わせ、設定推定率や設定分布が必要な条件だけ最終確認時にONにする。
