梅田さん、結論から言うと、このCSVでは**「深い沈みを返す」「直近REG/合算が枯れた台を返す」「日内1位が単独で抜けた日だけ強い」**という傾向が最も使えます。
ただし、ハッピージャグラー系はプロンプト指定どおり、機械割より **RB/REG確率 ＞ 合算 ＞ 設定5・6推定率分布 ＞ 機械割** を優先して評価しました。ハッピージャグラーは期待RB段階で整理し、合算1/135以下を成功の最低ラインとして扱う指定があるためです。

この回答は、単なる分析ではなく、あとでCodexがWebアプリへ実装できる「実装用の正本」を作る目的に合わせています。
また、CSV最新日は営業途中の可能性があるため除外し、未来情報を使わず、台番構成変更時は履歴をリセットするルールで集計しました。

## 2. 高内容日の定義

ハッピージャグラー特例として、設定5以上を成功扱いにし、設定4以下は失敗寄りに扱いました。プロンプト指定では、ハッピージャグラーは設定5・6推定率と設定4以下推定率を使う前提です。

| ラベル                 | 条件式                            | 用途 |                                      |                       |
| ------------------- | ------------------------------ | -- | ------------------------------------ | --------------------- |
| `highContent`       | `games >= 3000 && (p56 >= 0.50 |    | (rbRate <= 310 && combined <= 145))` | 前回高内容からの日数、直近高内容回数に使用 |
| `strongHighContent` | `games >= 4000 && (p56 >= 0.70 |    | (rbRate <= 270 && combined <= 135))` | 強い内容の履歴確認             |
| `midHighContent`    | `games >= 2500 && (p56 >= 0.30 |    | (rbRate <= 330 && combined <= 150))` | 参考の中間ラベル              |

`p56` は、BIGとREGを設定1〜6の確率へ当てはめ、対数尤度で正規化して算出した `設定5推定率 + 設定6推定率` です。

## 5. 100点満点ロジック

### 点数式

```text
score = clamp(
  40
  + (angle14 <= -100 ? 16 : angle14 <= -60 ? 10 : angle14 <= -30 ? 5 : 0)
  + (diff28 <= -4000 ? 10 : diff28 <= -2500 ? 7 : diff28 <= -1000 ? 4 : 0)
  + (combined28 >= 160 ? 10 : combined14 >= 163 ? 7 : combined14 >= 158 ? 4 : 0)
  + (rbRate7 >= 500 ? 8 : rbRate7 >= 400 ? 5 : 0)
  + (rbRate42 >= 400 ? 6 : 0)
  + (daysSinceHigh >= 4 && daysSinceHigh <= 14 ? 9 : daysSinceHigh >= 15 && daysSinceHigh <= 28 ? 5 : daysSinceHigh >= 29 && daysSinceHigh <= 60 ? 3 : 0)
  + (highContentCount28 <= 1 ? 5 : highContentCount28 <= 2 ? 2 : 0)
  + (games14 >= 15000 ? 4 : games7 >= 7000 ? 2 : 0)
  - (diff7 >= 1500 ? 12 : diff7 >= 500 ? 6 : 0)
  - (combined7 <= 145 ? 10 : combined7 <= 150 ? 5 : 0)
  - (highContentCount14 >= 3 ? 8 : 0)
  - (prevDiff >= 1500 && prevCombined <= 145 ? 8 : 0)
  - (daysSinceHigh <= 3 && prevHighContent ? 5 : 0)
  - (games7 < 5000 ? 4 : 0),
  0,
  100
)
```

### 指標定義

| 指標名                 | 計算式                       | 使う履歴範囲             | 欠損・低G数の扱い         | 未来情報を含まない理由    |
| ------------------- | ------------------------- | ------------------ | ----------------- | -------------- |
| `historyDays`       | 同一台番・同一区間の過去営業日数          | 台番リセット後            | 21未満は採用条件対象外      | 実績日前の履歴のみ      |
| `diffN`             | 過去N営業日の差枚合計               | 3,5,7,14,21,28,42日 | 存在する履歴のみ、採用は21日以上 | 実績日前だけ         |
| `gamesN`            | 過去N営業日のG数合計               | 7,14,28,42日        | 低G数は危険・減点         | 実績日前だけ         |
| `rbRateN`           | `gamesN / rbN`            | 3,5,7,42日          | RB0なら∞            | 実績日前だけ         |

# 検証方法
1. Webアプリで対象店舗「ワンダーランド南ヶ丘店」、対象機種「ハッピージャグラーＶＩＩＩ」を指定する。
2. Webアプリの入力期間が予測日基準の場合、2025-07-25〜2026-07-01を入力する。
3. 翌営業日実績として2025-07-26〜2026-07-02が集計されることを確認する。
4. 最新日2026-07-03が除外されていることを確認する。
5. 履歴リセット日 2025-07-04、2025-11-06、2026-02-04 をまたいで履歴がつながっていないことを確認する。
6. 「設定分布を表示」は最初OFFで照合し、選択台数、総G数、BB、RB、差枚、平均差枚、機械割を合わせる。
7. 設定5・6推定率や設定分布の確認時だけ「設定分布を表示」をONにする。
8. 各採用条件について、回答内の選択台数、総G数、BB数、RB数、BB確率、RB確率、合算、平均差枚、機械割と照合する。
9. 該当日付・台番一覧をWebアプリの該当台と1件ずつ突き合わせる。
10. ラベル名だけ実装して終わらせず、条件式をWebアプリのバックテストで再現できる形に落とし込む。

# 実装完了条件
- Webアプリ上で実際にバックテストを回し、回答内に書いた採用条件ごとの選択台数、総G数、BB確率、RB/REG、合算、平均差枚、機械割と照合する。
- Webアプリ側のバックテスト結果と回答内のバックテスト結果が、実用上許容できる範囲まで一致しない限り、実装完了扱いにしない。
- 許容範囲は、選択台数、総G数、BB数、RB数などの母数がほぼ一致し、確率、機械割、平均差枚の差が丸め誤差や表示単位差で説明できる程度とする。
- 回答内では整合しているのにWebアプリで一致しない場合は、条件式、最新日除外、未来情報除外、対象機種名、台番、履歴計算、通常日/イベント日の分岐、集計期間の違いを疑い、Webアプリ上で再検証しながら修正する。
- ただし、同じ条件について主要なズレ原因を3つ確認しても一致しない場合、または30分以上かかる場合は、通常採用として有効化せず、未採用理由を照合ログに記録する。
- 回答内の条件式、該当日付・台番一覧、集計表が最初から矛盾している条件は、Webアプリ側で無理に補正して合わせない。
- 採用条件のラベル名や期待値表示だけを写して終わらせず、実際にWebアプリのバックテストで再現できる条件式に落とし込む。
- 順位、次点差、近隣、履歴不足の定義が曖昧な条件は、ラベルだけ実装せず参考条件として扱う。
- Webアプリで回答値を再現できない条件は、通常採用条件として残さず、未採用理由を照合ログに記録する。
- Webアプリ照合では、最初から全条件で設定分布を表示しない。原則OFFで主要成績を合わせ、設定推定率や設定分布が必要な条件だけ最終確認時にONにする。
- Webアプリ実測ログと照合台帳を残す。
