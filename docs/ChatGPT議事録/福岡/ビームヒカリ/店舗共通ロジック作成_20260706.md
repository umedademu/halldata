## 2. 結論

今回、Webアプリへ通常採用してよい店舗共通条件は、1本に絞ります。

```text
SC_FREE_MAIN_UNPAID_ANGLE_RHYTHM
historyDays >= 14
&& daysSinceHighContent >= 4
&& daysSinceHighContent <= 14
&& diff14 >= -9000
&& diff14 <= -1500
&& angle7 >= -350
&& angle7 <= -70
&& lossStreak >= 2
&& lossStreak <= 6
&& storeCommonRiskCount == 0
```

この条件は、10機種すべてにまたがり、2,095台、総G数8,915,598G、平均差枚+163.6枚、機械割101.28%、勝率41.8%でした。強い爆発条件というより、店舗全体で共通している「ほどよい未返済・沈み角度・2〜6連敗・高内容後の冷却済み」を拾う条件です。

通常日専用・イベント日専用ロジックは作りません。特定日は全体成績が上がりますが、効いている履歴パターン自体は同じで、専用化すると「イベント日は強く見える」だけを過剰に取り込みやすいです。点数式には特定日・曜日・月初月末・ゾロ目などの日付そのものを一切入れません。

## 3. この回答で作る店舗共通スコアの位置づけ

`storeCommonScore` は、既存の機種別狙い度を置き換えるものではありません。

使い方は以下です。

| 状態             | 扱い                            |
| -------------- | ----------------------------- |
| 機種別スコアも店舗共通も強い | 本命寄り。機種別根拠に店舗全体のクセが重なる        |
| 機種別だけ強い        | 機種固有候補。店舗共通危険がなければ候補、危険ありなら減額 |
| 店舗共通だけ強い       | 穴候補。機種別本命が薄い日の補助候補            |
| 機種別は強いが店舗共通危険  | 見送りまたは大幅警戒                    |
| 店舗共通スコアが低い     | 機種別で強くても過信しない                 |

CSV内に既存の `狙度` がある機種もありましたが、欠損機種があり、また翌日実績との整合が悪い機種があったため、店舗共通ロジックの入力にも、最終採用の掛け合わせバックテストにも使いません。Webアプリ側で既存の機種別ロジックを再計算した後に、掛け合わせ表示を行う前提です。

## 5. 高内容判定の正規化

高内容判定の入口だけ、機種タイプ別に分けます。いったん `isHighContent` などへ変換した後は、全機種で同じ点数式を使います。

| 機種タイプ    | `isHighContent`                                                      | `isStrongHighContent`                                                | 注意                     |                             |   |                 |                    |
| -------- | -------------------------------------------------------------------- | -------------------------------------------------------------------- | ---------------------- | --------------------------- | - | --------------- | ------------------ |
| JUGGLER  | `g >= 3000 && combinedRate <= 145 && rbRate <= 320 && diff >= -1500` | `g >= 4500 && combinedRate <= 135 && rbRate <= 290 && diff >= -1000` | RB率を最優先、合算を次点、差枚は低品質除外 |                             |   |                 |                    |
| AT_SMART | `g >= 3000 && (diff >= 1500                                          |                                                                      | payout >= 106)`        | `g >= 3500 && (diff >= 3000 |   | payout >= 110)` | 機械割・差枚を主軸。BB/RBは参考 |

共通変数は以下です。

| 共通変数                         | 意味                    |
| ---------------------------- | --------------------- |
| `historyDays`                | 同一台番・同一設置セグメントの過去営業日数 |
| `daysSinceHighContent`       | 前回高内容からの営業日数。過去なしは999 |
| `daysSinceStrongHighContent` | 前回強高内容からの営業日数         |
| `highContentCount3/7`        | 直近3/7営業日の高内容回数        |
| `strongHighContentCount7`    | 直近7営業日の強高内容回数         |
| `diff7/diff14`               | 直近7/14営業日の累計差枚        |
| `angle7`                     | `diff7 / g7 * 1000`   |
| `lossStreak`                 | 前日までの連続マイナス日数         |
| `g7/g14`                     | 直近7/14営業日の合計G数        |
| `prevHighContent`            | 前営業日が高内容だったか          |
| `storeCommonRiskCount`       | 店舗共通危険条件数             |
| `storeCommonBoostCount`      | 店舗共通強化条件数             |
| `storeCommonRankInMachine`   | スコア計算後の同一機種内順位        |

## 6. 通常日・イベント日を分けるべきかの判断

分けません。

| 条件                                 |     通常日 |   イベント日 | 判断              |
| ---------------------------------- | ------: | ------: | --------------- |
| 全母集団                               |  99.39% | 100.87% | イベント日の投入量・稼働が強い |
| `SC_FREE_MAIN_UNPAID_ANGLE_RHYTHM` | 100.88% | 102.41% | 同じ履歴条件が両方でプラス   |
| `SC_STAGE_WEAK_BOOST6_RISK0`       | 100.71% | 102.39% | イベントで強いが通常もプラス  |
| `SC_SKIP_SCORE75_RISK2`            |  96.82% |  98.76% | 見送りは両方で弱い       |

イベント日は成績が上振れますが、日付そのものの差ではなく「同じ台履歴条件がイベント日により強く出ている」形です。専用ロジックを作るとイベント日の強さを条件に混ぜ込みやすいため、今回は全日共通のみです。

店舗共通ロジック名：
ビームヒカリ_storeCommonScore_v1

作るロジック：
- 全日共通の storeCommonScore を必ず作る。
- 通常日専用 storeCommonScoreNormalDay は作らない。
- イベント日専用 storeCommonScoreEventDay は作らない。
- 理由：CSVの特定日列で通常日・イベント日を比較したが、履歴パターンは同方向で、イベント日は同条件の期待値が強く出るだけ。日付そのものを点数化しないため、専用ロジック化はしない。

既存機種別ロジック：
- 残す。
- 店舗共通スコアは置き換えではなく、補助・信頼度強化・危険判定として使う。
- 既存の機種別スコアと店舗共通スコアを並列表示する。
- CSV内の既存「狙度」「次差」は店舗共通スコアの入力に使わない。

# 日付定義

スコア日：
着席対象日の前営業日。例：5/14スコアは5/15に座るべき度。

着席対象日：
スコア日の翌営業日。実際に座るか判断する日。

実績日：
バックテストでG数、BB、RB、差枚、機械割を集計する日。原則として着席対象日と同じ。

スコア日と実績日の対応：
scoreDate → targetDate/resultDate。
例：5/14スコア → 5/15実績。

回答内バックテストの実績日範囲：
2025-07-20〜2026-07-03。

Webアプリ入力期間：
2025-07-19〜2026-07-02。
理由：Webアプリが予測日基準で入力し、翌営業日実績を集計する前提のため、回答内実績日より1営業日前を入力する。

除外した最新日：
2026-07-04。
理由：CSV内の最新日は未完成データの可能性があるため除外。

通常日・イベント日の定義：
CSVの「特定日」列を正とする。
- 特定日=はい → イベント日
- 特定日=いいえ → 通常日

禁止：
- 特定日だから加点、イベント日だから加点は禁止。
- 曜日、月初、月末、ゾロ目、3の付く日、6の付く日などの日付ルールを直接点数化しない。
- 機種名や固定台番を直接優遇しない。
- ジャグラー専用店舗共通スコア、AT専用店舗共通スコアは作らない。

# 履歴・台番・欠損処理

履歴は同一機種・同一台番・同一設置セグメントで追う。
台番が変わった場合、増台・減台・島移動・同一台番の連続存在が切れた場合は履歴をリセットする。
旧台番と新台番を設置順や島内ポジションでつながない。
CSVに存在しない日付は営業日カウントに含めない。
G数0日は営業日として存在扱いにするが、低情報・危険判定に使う。
historyDays < 14 は通常採用不可。

- BB数
- RB数
- BB確率
- RB確率
- 合算確率
- 平均差枚
- 機械割
- 勝率
