# 2. 高内容日の定義

ネオアイムジャグラーEXなので、評価は **RB/REG確率 ＞ 合算確率 ＞ 機械割** の順に置きました。設定列は最終ロジックの説明変数には使っていません。検証ラベルとしては、ネオアイム特例に従い、設定5・6推定率を重視しました。ネオアイムでは設定5・6級に座れた割合を最重要指標とする指定があり、設定5・6推定率は設定5推定率＋設定6推定率として扱います。

| ラベル         | 条件式                         | 用途            |                                                      |          |
| ----------- | --------------------------- | ------------- | ---------------------------------------------------- | -------- |
| highContent | `(G >= 2500 && p56 >= 0.30) |               | (G >= 3000 && rbRate <= 310 && combinedRate <= 145)` | 過去の高内容履歴 |
| strongHigh  | `(G >= 3000 && p56 >= 0.50) |               | (G >= 3500 && rbRate <= 270 && combinedRate <= 135)` | 強い高内容履歴  |
| p56         | 設定5推定率 + 設定6推定率             | ネオアイムの成功代理指標  |                                                      |          |
| p4low       | 1 - p56                     | 設定4以下側の失敗代理指標 |                                                      |          |

設定推定は、ネオアイムの設定別BIG/REG確率を使い、BBとRBを別々に二項分布の対数尤度で計算して正規化しました。使用した設定別ボーナス確率は、プロンプト内のネオアイム設定値に基づきます。

# 3. 設定師のクセの仮説

最も強かったのは、**短中期でしっかり沈み、直近REGが枯れている台を戻すクセ**です。特に `diff5 <= -2000 && diff14 <= -3000 && rbRate7 >= 400` は、選択24台でRB 1/278.2、合算1/132.2、平均差枚+395.2、機械割104.06%となり、今回の本命条件にできます。

次に強かったのは、**深沈み＋REG枯れの状態で、直近2〜14日前に強高内容を踏んだ台**です。これは「出し切り後の据え置き」ではなく、いったん強い内容を見せたあとに再び沈んだ台を拾う形が強いです。

自由探索では、**長期REG枯れ・強高内容から42日以上空き・直近3日角度が急落**という条件が、点数上位に出ない台も拾いながらRB 1/276.9、勝率65.2%になりました。これは点数ロジックより優先してよい自由度MAX条件です。

# 13. 最終結論

この機種では、100点満点ロジックは毎日の候補整理に有効ですが、主軸は **段階的採用条件＋自由度MAX条件** に置くのが現実的です。最も打つ価値があるのは、短中期で沈み、REGが枯れ、まだ返済未完了に見える台です。イベント日専用・通常日専用の別ロジックは、件数と再現性の面で今回は作らず、全日共通のみを採用します。

# 対象
対象店舗：123+N東雲店
対象機種：ネオアイムジャグラーEX
実装すべき機種別ロジック名：
123N東雲_ネオアイムEX_全日共通_沈みREG枯れ返済ロジック_v1

通常日専用ロジックとイベント日専用ロジック：
今回は作らない。
理由：
CSVの特定日列で通常日/イベント日を分けて検証したが、件数不足とブレがあり、通常日専用・イベント日専用を別実装すると過剰最適化になりやすい。
Webアプリでは全日共通ロジックのみを「機種別」列へ表示する。
「通常日」「特定日」列の専用ロジックは今回は追加しない。

# 集計プロトコル正本
対象店舗：123+N東雲店
対象機種：ネオアイムジャグラーEX
回答内バックテストの実績日範囲：2026-02-28〜2026-06-22
Webアプリ入力期間：2026-02-27〜2026-06-21
差がある理由：
Webアプリが「予測日を入力し、翌営業日実績を集計する」前提のため、回答内実績日よりWebアプリ入力期間を1日ずらす。
もしWebアプリ側が実績日を直接指定する仕様なら、2026-02-28〜2026-06-22で照合する。

除外した最新日：2026-06-23
履歴計算開始日：2026-02-06
履歴不足：historyDays < 21 は score=0 または低信頼扱いとし、通常採用条件から除外する。
履歴リセット日：
台番をまたぐ接続はしない。1044番台は2026-03-01まで存在し、その後は終了扱い。他台番に接続しない。
店休日・欠損日：
全台G数0の日はなし。個別台G数0はその台の実績として保持する。
対象機種名の扱い：
ネオアイムジャグラーEXのみ。機種統合なし。
設定分布表示：
原則OFFで選択台数、総G数、BB、RB、確率、差枚、機械割を照合する。
設定5・6推定率や設定分布を最終確認する条件だけONにする。

# ネオアイム特例
ネオアイムジャグラーEXでは、設定5・6級だけを成功扱い、設定4以下は失敗寄りとして扱う。
設定推定率は、各台の総G数G、BB回数B、RB回数Rから、設定別BIG確率とREG確率を使って対数二項尤度で計算する。
設定5・6推定率 = 設定5推定率 + 設定6推定率
設定4以下推定率 = 設定1〜4推定率の合計

ネオアイム設定値：
設定1 BIG 1/273.1 REG 1/439.8 合成 1/168.48
設定2 BIG 1/269.7 REG 1/399.6 合成 1/161.02
設定3 BIG 1/269.7 REG 1/331.0 合成 1/148.61
設定4 BIG 1/259.0 REG 1/315.1 合成 1/142.15
設定5 BIG 1/259.0 REG 1/255.0 合成 1/128.49
設定6 BIG 1/255.0 REG 1/255.0 合成 1/127.50

# 高内容定義
highContent:
(G >= 2500 && p56 >= 0.30) || (G >= 3000 && rbRate <= 310 && combinedRate <= 145)

strongHigh:
(G >= 3000 && p56 >= 0.50) || (G >= 3500 && rbRate <= 270 && combinedRate <= 135)

p56:
設定5推定率 + 設定6推定率

p4low:
1 - p56

# 指標定義
historyDays：
同一台番で、予測日前に存在する過去営業日数。台番をまたがない。

diffN：
予測日前N営業日の同一台番の差枚合計。

gN：
予測日前N営業日の同一台番のG数合計。

bbN：
予測日前N営業日の同一台番のBB合計。

rbN：
予測日前N営業日の同一台番のRB合計。

rbRateN：
gN / rbN。rbN == 0 の場合は Infinity。

bbRateN：
gN / bbN。bbN == 0 の場合は Infinity。

combinedN：
gN / (bbN + rbN)。BB+RB == 0 の場合は Infinity。

angleN：
diffN / gN * 1000。
単位は枚/1000G。マイナスが大きいほど急角度の沈み。
gN == 0 の場合は0または無効値。

highCountN：
予測日前N営業日に highContent を満たした回数。

strongCountN：
予測日前N営業日に strongHigh を満たした回数。

lossStreak：
予測日前から連続して差枚がマイナスの営業日数。

winStreak：
予測日前から連続して差枚がプラスの営業日数。

daysSinceHigh：
直近 highContent からの経過営業日数。
過去にない場合は大きな値として扱う。

daysSinceStrong：
直近 strongHigh からの経過営業日数。
過去にない場合は大きな値として扱う。

prevDiff：
予測日前日の同一台番の差枚。

prevG：
予測日前日の同一台番のG数。

prevBB：
予測日前日の同一台番のBB。

prevRB：
予測日前日の同一台番のRB。

prevP56：
予測日前日の同一台番のp56。

prevHigh：
予測日前日が highContent なら true。

prevStrong：
予測日前日が strongHigh なら true。

prevRbRate：
予測日前日のRB確率。prevG / prevRB。prevRB == 0 は Infinity。

prevCombined：
予測日前日の合算確率。prevG / (prevBB + prevRB)。BB+RB == 0 は Infinity。

rank：
同一実績日、同一機種、historyDays>=21の台だけでscore降順に順位付け。
同点は同順位。

topGap：
rank==1 の台だけ、1位score - 2番目に高い異なるscore。
1位同点または2番目が存在しない場合は0。
rank!=1は0。

# 100点満点ロジック
基礎点：
historyDays >= 21 の場合 40点。
historyDays < 21 の場合 0点、通常採用条件から除外。

加点：
diff5 <= -1500：+8
diff14 <= -3000：+10
diff28 <= -4000：+10
lossStreak >= 3：+6
rbRate7 >= 400：+10
rbRate14 >= 400：+6
daysSinceHigh >= 8 && daysSinceHigh <= 35：+6
daysSinceStrong >= 42：+8
highCount7 == 0：+4
g7 >= 7000：+4

減点：
g7 < 4000：-8
diff7 >= 2500：-8
diff14 >= 4000：-8
prevStrong && prevDiff >= 1500：-10
highCount7 >= 2：-6
winStreak >= 3 && diff14 >= 0：-6

上限：
score > 100 は 100。

下限：
score < 0 は 0。

# 強化条件
深沈みREG枯れ：
diff5 <= -2000 && diff14 <= -3000 && rbRate7 >= 400

強高内容後の再沈み：
diff14 <= -3000 && rbRate7 >= 400 && daysSinceStrong >= 2 && daysSinceStrong <= 14

長期REG枯れ急落：
rbRate28 >= 350 && daysSinceStrong >= 42 && angle3 <= -100

# 危険条件
出し切り強高内容翌日：
prevStrong && prevDiff >= 1500

低稼働履歴：
g7 < 4000

高内容過密：
highCount7 >= 2

# 見送り条件
見送り_高内容過密：
historyDays >= 21 && score >= 70 && highCount7 >= 2

# 検証方法
必ずWebアプリ上で実際にバックテストを回し、回答内に書いた採用条件ごとの選択台数、総G数、BB確率、RB/REG、合算、平均差枚、機械割と照合する。
Webアプリ側のバックテスト結果と回答内のバックテスト結果が、実用上許容できる範囲まで一致しない限り、実装完了扱いにしない。
ここでいう許容範囲は、選択台数、総G数、BB数、RB数などの母数がほぼ一致し、確率、機械割、平均差枚の差が丸め誤差や表示単位差で説明できる程度とする。
回答内では整合しているのにWebアプリで一致しない場合は、条件式、最新日除外、未来情報除外、対象機種名、台番、履歴計算、通常日/イベント日の分岐、集計期間の違いを疑い、Webアプリ上で再検証しながら修正する。
ただし、同じ条件について主要なズレ原因を3つ確認しても一致しない場合、または30分以上かかる場合は、通常採用として有効化せず、未採用理由を照合ログに記録する。
回答内の条件式、該当日付・台番一覧、集計表が最初から矛盾している条件は、Webアプリ側で無理に補正して合わせない。
採用条件のラベル名や期待値表示だけを写して終わらせず、実際にWebアプリのバックテストで再現できる条件式に落とし込む。
該当日付・台番一覧がある場合は、Webアプリの該当台と1件ずつ突き合わせる。
順位、次点差、近隣、履歴不足の定義が曖昧な条件は、ラベルだけ実装せず参考条件として扱う。
Webアプリで回答値を再現できない条件は、通常採用条件として残さず、未採用理由を照合ログに記録する。
Webアプリ照合では、最初から全条件で設定分布を表示しない。原則OFFで主要成績を合わせ、設定推定率や設定分布が必要な条件だけ最終確認時にONにする。
