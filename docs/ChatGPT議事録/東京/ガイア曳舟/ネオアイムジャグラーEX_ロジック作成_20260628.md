分析目的は「高設定を入れる場所のクセを分析し、翌日の狙い台を決める100点満点ロジックを作る」こと、かつ最終成果物として100点ロジック・段階的採用条件・自由度MAX条件を分ける指定だと解釈して処理しました。
対象機種はファイル名・列内容から **ガイア曳舟 / ネオアイムジャグラーEX** として扱い、ネオアイム特例どおり、期待機械割ではなく **期待RB段階** と **設定5・6推定率** を重視しました。

## 2. 高内容日の定義

ネオアイムはREG差が大きいので、指定どおり **設定5・6級に座れたか** を最重要視しました。設定推定は、BIG・REGを別々の二項分布として扱い、設定1〜6の重みを正規化し、`p56 = p5 + p6` を設定5・6推定率として使っています。

過去履歴用の高内容日は、次で固定しました。

```text
high56 = G >= 2500 && p56 >= 0.50
strong56 = G >= 3000 && p56 >= 0.70
```

この `high56` は当日を判定するためには使わず、**過去日の履歴特徴** としてのみ使っています。

## 3. 見えた設定師のクセ

最も強かったのは、単純な凹み上げではなく、**直近3日以内に高内容っぽい履歴があり、その後もREGが枯れていて、14日差枚がまだ返済未完了の台** でした。

特に強かった軸は次です。

| クセ仮説       | データ上の評価                                                        |
| ---------- | -------------------------------------------------------------- |
| 直近高内容のリトライ | 強い。`high56cnt3 >= 1` が採用条件の入口                                  |
| REG枯れからの返し | 強い。`rbRate7 >= 350`、`rbRate14 >= 400`、`rbRate21 >= 400` が有効    |
| 返済未完了      | 強い。`diff14 <= -1000` と組むとRB・合算が改善                              |
| 単純な毎日1位    | 弱い。順位だけではRB 1/392.4で採用不可                                       |
| 次点差        | 補助として有効。`rank == 1 && topGap >= 8` は機械割は上がるが、RBは1/353.3で本命には不足 |
| 特定日優遇      | 明確ではない。特定日だけの専用式は作らない方がよい                                      |

## 5. 完成した100点満点ロジック

ロジック名案：

```text
ガイア曳舟_ネオアイムジャグラーEX_全日共通_リトライ返済未完ロジック_v1
```

点数は全台に付けますが、実戦の主軸は点数単体ではなく、後述の段階的採用条件です。

```text
score = min(100, max(0, 50 + 加点合計 - 減点合計))
```

## 12. 実戦での使い方

毎日の順位付けには **100点満点score** を使います。ただし、score上位をそのまま打つのではなく、まず `score >= 80 && boostCount < 4` を見送り、次に段階条件を確認してください。

実戦優先順位は次です。

1. **自由本命 / 弱本命RB300**
   `high56cnt3 >= 1 && rbRate7 >= 350 && diff14 <= -1000 && score >= 75`

2. **強RB280**
   `high56cnt3 >= 1 && rbRate21 >= 400 && rbRate7 >= 350`
   件数は少ないが、出た日は強く見る。

3. **本命RB290**
   `high56cnt3 >= 1 && rbRate14 >= 400 && diff14 <= -1000`

4. **広めRB310**
   入口。複数候補がある日は、score・boostCount・topGapで優先順位を付ける。

5. **rank1 topGap>=8**
   単独では本命にしない。段階条件と重なった時だけ補助。

## 13. 最終結論

この機種では、**100点満点ロジック単体を主軸にするべきではありません**。scoreは候補抽出・順位付けの土台として使い、実戦の座る判断は **段階的採用条件、特に弱本命RB300 / 自由本命** を主軸にするべきです。

最終判断は次の順番です。

```text
1. 見送り条件を確認
2. 弱本命RB300 / 自由本命に該当するか確認
3. 強RB280・本命RB290に該当するか確認
4. 広めRB310なら、score・boostCount・topGapで補助判断
5. score上位だけ、rank1だけの日は無理に座らない
```

```text
p56 = p5 + p6
p4low = p1 + p2 + p3 + p4

# 検証方法

必ずWebアプリ上で実際にバックテストを回し、以下を照合する。

実装完了条件：
- Webアプリ上で実際にバックテストを回し、回答内に書いた採用条件ごとの選択台数、総G数、BB確率、RB/REG、合算、平均差枚、機械割と照合する
- Webアプリ側のバックテスト結果と回答内のバックテスト結果が、実用上許容できる範囲まで一致しない限り、実装完了扱いにしない
- ここでいう許容範囲は、選択台数、総G数、BB数、RB数などの母数がほぼ一致し、確率、機械割、平均差枚の差が丸め誤差や表示単位差で説明できる程度とする
- 一致しない場合は、条件式、最新日除外、未来情報除外、対象機種名、台番、履歴計算、通常日/イベント日の分岐、集計期間の違いを疑い、Webアプリ上で再検証しながら修正する
- 採用条件のラベル名や期待値表示だけを写して終わらせず、実際にWebアプリのバックテストで再現できる条件式に落とし込む
- 該当日付・台番一覧がある場合は、Webアプリの該当台と1件ずつ突き合わせる
- 順位、次点差、近隣、履歴不足の定義が曖昧な条件は、ラベルだけ実装せず参考条件として扱う
- Webアプリで回答値を再現できない条件は、通常採用条件として残さず、未採用理由を照合ログに記録する

照合時に特に確認すること：
1. 2026-06-10を完全に除外しているか
2. 2026-02-06〜2026-02-26を履歴作成のみにしているか
3. バックテスト対象が2026-02-27〜2026-06-09になっているか
4. high56を対象当日ではなく過去日だけで計算しているか
5. rbRate7/14/21が対象日より前の履歴だけで計算されているか
6. score、rank、topGapが上記定義どおりか
```
