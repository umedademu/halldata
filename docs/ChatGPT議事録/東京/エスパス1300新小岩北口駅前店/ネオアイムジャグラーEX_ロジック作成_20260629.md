## 2. 高内容日の定義

| 区分   | 条件式                        | 位置づけ            |
| ---- | -------------------------- | --------------- |
| 準高内容 | `G >= 2500 && p56 >= 0.30` | 直近の見せ場・処遇履歴に使う  |
| 高内容  | `G >= 3000 && p56 >= 0.50` | 高設定投入履歴の主判定     |
| 強高内容 | `G >= 4000 && p56 >= 0.70` | 強い処遇・据え/続行判定に使う |

`p56` は当日結果から計算する検証ラベルです。翌日の予測スコア計算では、判定対象日より前の日の `p56` だけを履歴として使い、当日・翌日のBB/RB/G数/差枚は一切使いません。未来情報を使わないというプロンプト条件に合わせています。

## 6. 指標定義

## 11. 最終結論

この機種では、**100点満点ロジックは毎日の順位付け用**、**段階的採用条件はWebアプリ条件列での強弱表示用**、**自由MAX条件は条件が出た日だけ優先する本命ルール**として分けるのが最も現実的です。

実戦優先順位は次の通りです。

|  優先 | 見る条件             | 判断             |
| --: | ---------------- | -------------- |
|   1 | `強_急沈みRB残り`      | 最も安定。該当時は強く見る  |
|   2 | `自由MAX_ホット強内容続行` | 件数は少なめだが出た日は優先 |
|   3 | `本命_1位90差5`      | 日別1位の強候補       |
|   4 | `弱め本命_1位85差5`    | 座れる日を増やす候補     |
|   5 | `広め_スコア80強化4`    | 候補入口。単独では過信しない |

# 17. 検証方法
1. CSV最新日2026-06-27を除外する。
2. 履歴計算開始日を2025-09-01にする。
3. Webアプリのバックテスト入力期間を2025-09-21〜2026-06-25にする。
4. Webアプリが実績日指定の場合は、2025-09-22〜2026-06-26で照合する。
5. 設定分布表示はまずOFF。
6. 各条件の選択台数、総G数、BB、RB、BB確率、RB確率、合算、平均差枚、機械割、勝率を照合する。
7. 設定推定率の最終確認時だけ設定分布表示をONにする。
8. 該当日付・台番一覧をWebアプリの該当台と1件ずつ突き合わせる。

実装完了条件：
- Webアプリ上で実際にバックテストを回し、回答内に書いた採用条件ごとの選択台数、総G数、BB確率、RB/REG、合算、平均差枚、機械割と照合する。
- Webアプリ側のバックテスト結果と回答内のバックテスト結果が、実用上許容できる範囲まで一致しない限り、実装完了扱いにしない。
- ここでいう許容範囲は、選択台数、総G数、BB数、RB数などの母数がほぼ一致し、確率、機械割、平均差枚の差が丸め誤差や表示単位差で説明できる程度とする。
- 回答内では整合しているのにWebアプリで一致しない場合は、条件式、最新日除外、未来情報除外、対象機種名、台番、履歴計算、通常日/イベント日の分岐、集計期間の違いを疑い、Webアプリ上で再検証しながら修正する。
- ただし、同じ条件について主要なズレ原因を3つ確認しても一致しない場合、または30分以上かかる場合は、通常採用として有効化せず、未採用理由を照合ログに記録する。
- 回答内の条件式、該当日付・台番一覧、集計表が最初から矛盾している条件は、Webアプリ側で無理に補正して合わせない。
- 採用条件のラベル名や期待値表示だけを写して終わらせず、実際にWebアプリのバックテストで再現できる条件式に落とし込む。
- 該当日付・台番一覧がある場合は、Webアプリの該当台と1件ずつ突き合わせる。
- 順位、次点差、近隣、履歴不足の定義が曖昧な条件は、ラベルだけ実装せず参考条件として扱う。
- Webアプリで回答値を再現できない条件は、通常採用条件として残さず、未採用理由を照合ログに記録する。
- Webアプリ照合では、最初から全条件で設定分布を表示しない。原則OFFで主要成績を合わせ、設定推定率や設定分布が必要な条件だけ最終確認時にONにする。
