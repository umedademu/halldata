## 結論

対象は **エスパス日拓上野本館 / ネオアイムジャグラーEX** です。今回の最終成果物は分析コメントではなく、後段のCodexがWebアプリへ実装できる仕様書として固定します。プロンプト上も、最終目的は分析レポートではなく「実装用の正本」を作ること、実装に使う内容は最後の **実装用正本** と **Codex貼り付け用 実装依頼** に集約することが指定されています。

この機種では、単純な「凹み上げ」よりも、**過去28日の56濃度がある台を、前回高内容から3〜8営業日付近で再投入するクセ** と、**直近14日合算が生きているのに連敗している台をもう一度使うクセ** が強く出ました。特定日は全体平均としては通常日より強いですが、最終ロジックでは `特定日だから加点` は入れていません。日付種別そのものではなく、台ごとの履歴だけでスコア化します。

実戦優先順位は、次の順です。

1. **自由MAX_28RB連敗周期**：点数ロジックより優先してよい本命ルール
2. **最本命_28高内容周期3_8累積RB** / **強_合算残り火連敗**：REG・合算の裏付けが最も強い
3. **本命_28高内容濃度周期3_8**：56履歴と再投入周期を重視
4. **弱め本命_単独首位差10** / **広め_履歴56危険0**：候補拡張用
5. **見送り_1位僅差ブースト不足** に該当する1位台は、順位だけでは追わない

ネオアイムは設定5・6級だけを成功、設定4以下を失敗として扱う特例機種なので、平均差枚や機械割より **設定5・6推定率** を重視しました。

## 2. 高内容日の定義

ネオアイムの評価は、REG確率だけでなく、BIG・REGを別々に見た設定推定率を主軸にしました。設定推定率は、台ごとの `G / BB / RB` から設定1〜6の尤度を出し、正規化して算出する方式です。

| 判定           | 定義                                 | 用途             |
| ------------ | ---------------------------------- | -------------- |
| `p56_day`    | 当日G数・BB・RBから計算した設定5+6推定率           | バックテスト評価用      |
| `high56_day` | `G数 >= 4000 && p56_day >= 0.50`    | 過去履歴内の高内容日カウント |
| `p56Hist28`  | 予測日前28営業日のG数・BB・RB合計から計算した設定5+6推定率 | 実戦前に使える説明変数    |
| 成功扱い         | 設定5・6推定率が高い台                       | ネオアイム特例        |
| 失敗扱い         | 設定4以下推定率が高い台                       | ネオアイム特例        |

ネオアイムの段階的条件は、期待機械割ではなく期待RB 1/310、1/300、1/290、1/280、1/270の段階で整理する指定に合わせています。

# 5. 指標定義正本
historyDays：同一台番で予測日より前に存在する有効営業日数。
gamesN：同一台番の予測日前N営業日のG数合計。
diffN：同一台番の予測日前N営業日の差枚合計。
BBN：同一台番の予測日前N営業日のBB合計。
RBN：同一台番の予測日前N営業日のRB合計。
rbRateN：gamesN / RBN。RBN=0ならInfinity。
combinedRateN：gamesN / (BBN + RBN)。BBN+RBN=0ならInfinity。
p56_day：当日G数・BB・RBから計算する設定5・6推定率。評価用であり、当日予測には使わない。
high56_day：当日G数 >= 4000 && p56_day >= 0.50。過去履歴に入った後だけ使う。
p56Hist28：予測日前28営業日の games28, BB28, RB28 から計算した設定5・6推定率。
high56Count14：予測日前14営業日に high56_day が何回あったか。
daysSinceHigh56：予測日前の直近 high56_day から何営業日経過したか。直前営業日がhigh56なら1。過去にない場合はnull。
lossStreak：予測日前日から連続して差枚<0だった営業日数。
cumRbRate：同一台番リセット後、予測日前までの累積G数 / 累積RB。
cumCombinedRate：同一台番リセット後、予測日前までの累積G数 / 累積BB+RB。
boostCount：以下7項目の該当数。
  1) p56Hist28 >= 0.05
  2) rbRate28 <= 300
  3) combinedRate14 <= 140
  4) daysSinceHigh56 >= 3 && daysSinceHigh56 <= 8
  5) lossStreak >= 2
  6) games7 <= 30000
  7) cumCombinedRate <= 145
dangerCount：以下6項目の該当数。
  1) games7 > 35000
  2) cumRbRate > 360
  3) cumCombinedRate > 155
  4) diff28 <= -6000 && p56Hist28 < 0.05
  5) high56Count14 >= 5
  6) historyDays < 21
rank：同一実績日・同一機種・historyDays>=21の台をscore降順、同点は台番昇順で並べた順位。同点も別順位にする。
topGap：当該台のscore - 次順位台のscore。rank=1なら1位と2位の点差。最下位はnull。
勝率：差枚 > 0 の割合。
機械割：100 + 総差枚 / 総G数 / 3 * 100。

# 14. 実装完了条件
- Webアプリ上で実際にバックテストを回し、回答内に書いた採用条件ごとの選択台数、総G数、BB確率、RB/REG、合算、平均差枚、機械割と照合する。

- ここでいう許容範囲は、選択台数、総G数、BB数、RB数などの母数がほぼ一致し、確率、機械割、平均差枚の差が丸め誤差や表示単位差で説明できる程度とする。
- 回答内では整合しているのにWebアプリで一致しない場合は、条件式、最新日除外、未来情報除外、対象機種名、台番、履歴計算、通常日/イベント日の分岐、集計期間の違いを疑い、Webアプリ上で再検証しながら修正する。

- 回答内の条件式、該当日付・台番一覧、集計表が最初から矛盾している条件は、Webアプリ側で無理に補正して合わせない。
- 採用条件のラベル名や期待値表示だけを写して終わらせず、実際にWebアプリのバックテストで再現できる条件式に落とし込む。
- 該当日付・台番一覧がある場合は、Webアプリの該当台と1件ずつ突き合わせる。

- Webアプリ照合では、最初から全条件で設定分布を表示しない。原則OFFで主要成績を合わせ、設定推定率や設定分布が必要な条件だけ最終確認時にONにする。
