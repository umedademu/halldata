以下は、アップロードCSVをもとに作った **マルホン・ネオアイムジャグラーEX用の狙い台ロジック正本** です。
今回のプロンプトは「分析レポート」ではなく、後でCodexがWebアプリへ実装できる正本を作ることが目的なので、途中仮説と最終採用条件は分けて整理しています。

最新日の行は未完成データの可能性があるため除外し、当日前に分からない未来情報は点数・条件式に使っていません。 
また、ネオアイムは **設定5・6級に座れた割合を成功指標** とする特例に従い、RBだけではなくBIG/RBから計算した設定5・6推定率を検証指標にしました。

## 最終結論

このCSVでは、単純な「前日凹み」よりも、**過去35日で高内容履歴が多い台が、21日累計で沈んでいる時に返す** クセが最も実戦向きでした。

実戦優先順位は次の順です。

|  優先 | 条件                                                  | 使い方                                                  |
| --: | --------------------------------------------------- | ---------------------------------------------------- |
|   1 | `highContentCount35 >= 5 && diff21 <= -4000`        | 最本命。RB 1/259.5、合算 1/126.6、機械割 106.50%。件数20件なので過信は禁物。 |
|   2 | `highContentCount35 >= 5 && angle21 <= -50`         | 自由度MAXの主軸。45件でRB 1/275.2、合算 1/132.8、機械割 104.39%。     |
|   3 | `score >= 90`                                       | 点数ロジック上の本命閾値。62件でRB 1/280.3。                         |
|   4 | `rank == 1 && topGap >= 10`                         | 1位が抜けている日の弱め本命。64件でRB 1/292.9。                       |
|   5 | `rank == 1 && topGap >= 5`                          | 広め入口。109件でRB 1/307.3。                                |
| 見送り | `score >= 70 && prevP56 >= 0.50 && prevDiff >= 500` | 高スコアでも前日処遇完了気味。5件で機械割96.79%。                         |

通常日・イベント日は分けません。`特定日=はい` の方がややRBは軽いものの、専用ロジックを作るほど履歴パターンが分離しておらず、件数面でも過剰最適化になりやすいです。

## 2. 高内容日の定義

最終条件の履歴ラベルとして、次の3段階を使いました。設定列は説明変数には使っていません。設定5・6推定率は、BIG/RBの実績から設定1〜6の尤度を計算し、検証ラベル・履歴ラベルとしてだけ使いました。設定推定率は、設定ごとのBIG/REG確率から重みを計算し正規化する方式が指定されています。

## 3. 見えた設定師のクセ

一番強いクセは、**過去35日で高内容実績が多い台を完全には切らず、沈んだところで戻す** 動きです。固定台番優遇ではなく、`highContentCount35` という履歴実績で表現できるため、Webアプリ実装に向いています。

次に強いのは、**同一日の1位スコアが2位以下から離れている時だけ拾う** 形です。単純な毎日1位はRB 1/320前後まで落ちますが、`topGap >= 10` に絞るとRB 1/292.9まで改善しました。

弱かったのは、単純な低稼働狙い、単純な処遇完了台継続、広すぎるスコア閾値です。`score >= 85` は160件取れますがRB 1/329.0で、ネオアイムの採用条件としては弱めです。

# 3. ネオアイム評価指標

ネオアイムジャグラーEXでは、設定5・6級だけを成功扱いにする。
設定4以下は今回の狙い台ロジックでは失敗扱いにする。
採用条件は平均RBだけで判断せず、設定5・6推定率、設定4以下推定率、合算、平均差枚、機械割も併記する。

設定推定率：
各台について、総G数G、BIG回数B、REG回数Rを使う。
設定ごとのBIG確率、REG確率は以下。

設定1 BIG 1/273.1 REG 1/439.8 合成 1/168.48
設定2 BIG 1/269.7 REG 1/399.6 合成 1/161.02
設定3 BIG 1/269.7 REG 1/331.0 合成 1/148.61
設定4 BIG 1/259.0 REG 1/315.1 合成 1/142.15
設定5 BIG 1/259.0 REG 1/255.0 合成 1/128.49
設定6 BIG 1/255.0 REG 1/255.0 合成 1/127.50

logWeight(setting) =
logComb(G,B) + B*log(pB) + (G-B)*log(1-pB)
+
logComb(G,R) + R*log(pR) + (G-R)*log(1-pR)

最大logWeightを引いてexpし、設定1〜6の合計が1になるよう正規化する。
p56 = p5 + p6
p4lower = p1 + p2 + p3 + p4

# 4. 高内容ラベル定義

highContent:

4. 実績日は 2026-02-27〜2026-06-17 として翌営業日実績を集計する。
5. 設定分布表示は原則OFFで、まず選択台数、総G数、BB、RB、差枚、平均差枚、機械割を照合する。
6. 主要成績が合った後、設定5・6推定率や設定分布の最終確認だけ設定分布表示をONにする。
7. 条件ごとに、上記の該当一覧とWebアプリの該当台を1件ずつ突き合わせる。
8. 条件式、最新日除外、未来情報除外、対象機種名、台番、履歴計算、通常日/イベント日の分岐、集計期間の違いを確認する。
9. 同じ条件について主要なズレ原因を3つ確認しても一致しない場合、または30分以上かかる場合は、通常採用として有効化せず、未採用理由を照合ログに記録する。
10. 回答内の条件式、該当日付・台番一覧、集計表が最初から矛盾している条件は、Webアプリ側で無理に補正して合わせない。

実装完了条件：
- Webアプリ上で実際にバックテストを回し、回答内に書いた採用条件ごとの選択台数、総G数、BB確率、RB/REG、合算、平均差枚、機械割と照合する。
- Webアプリ側のバックテスト結果と回答内のバックテスト結果が、実用上許容できる範囲まで一致しない限り、実装完了扱いにしない。
- 許容範囲は、選択台数、総G数、BB数、RB数などの母数がほぼ一致し、確率、機械割、平均差枚の差が丸め誤差や表示単位差で説明できる程度とする。
- 採用条件のラベル名や期待値表示だけを写して終わらせず、実際にWebアプリのバックテストで再現できる条件式に落とし込む。
- 順位、次点差、近隣、履歴不足の定義が曖昧な条件は、ラベルだけ実装せず参考条件として扱う。
- Webアプリで回答値を再現できない条件は、通常採用条件として残さず、未採用理由を照合ログに記録する。
