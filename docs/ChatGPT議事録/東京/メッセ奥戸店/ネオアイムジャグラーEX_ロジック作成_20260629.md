以下は、添付CSVをもとにした **メッセ奥戸店 × ネオアイムジャグラーEX** の狙い台ロジック正本です。今回のプロンプトは、分析レポートではなく、あとでCodexが迷わず実装できる「実装用の正本」を作ることが目的とされているため、通常採用条件は、条件式・該当一覧・集計値が一致するものだけに絞りました。 また、ネオアイムは設定5・6級を成功、設定4以下を失敗寄りとして扱う特例があるため、RBだけでなく設定5・6推定率も重視しています。

## 1. 結論

この店のネオアイムは、**大きく凹んだ台を返す店ではなく、直近で高内容が複数回見えている台をさらに使う「加熱維持型」**です。

最終的な通常採用は次の3条件です。

| 優先 | 条件名         | 採用区分 | 実戦判断                                                  |
| -: | ----------- | ---- | ----------------------------------------------------- |
|  1 | 本命290       | 通常採用 | 最優先。件数は23台と少なめだが、RB 1/289.74、合算 1/135.90、平均差枚 +466.1枚 |
|  2 | 加熱維持296     | 通常採用 | 本命。RB 1/296.15、合算 1/139.19、平均差枚 +289.1枚               |
|  3 | 加熱維持310     | 通常採用 | 広め。RB 1/307.85、合算 1/145.22、平均差枚 +64.3枚                |
| 参考 | 三日RB保証286参考 | 参考表示 | 成績は最強だが12台のみ。通常採用の主軸にはしない                             |
| 避け | 前日大凹み見送り    | 見送り  | scoreが高くても前日-1000枚以下はRB 1/350.40まで悪化                  |

100点満点ロジックは毎日の順位付けには使えますが、実戦で座る優先順位は、**本命290 → 加熱維持296 → 加熱維持310 → 参考条件確認 → 前日大凹み見送り除外**の順が現実的です。

  - (highContentCount14 == 0 ? 8 : 0)

  - (diff14 <= -3000 ? 4 : 0)

- Webアプリ上で実際にバックテストを回し、回答内に書いた採用条件ごとの選択台数、総G数、BB確率、RB/REG、合算、平均差枚、機械割と照合する
- Webアプリ側のバックテスト結果と回答内のバックテスト結果が、実用上許容できる範囲まで一致しない限り、実装完了扱いにしない
- ここでいう許容範囲は、選択台数、総G数、BB数、RB数などの母数がほぼ一致し、確率、機械割、平均差枚の差が丸め誤差や表示単位差で説明できる程度とする
- 回答内では整合しているのにWebアプリで一致しない場合は、条件式、最新日除外、未来情報除外、対象機種名、台番、履歴計算、通常日/イベント日の分岐、集計期間の違いを疑い、Webアプリ上で再検証しながら修正する
- ただし、同じ条件について主要なズレ原因を3つ確認しても一致しない場合、または30分以上かかる場合は、通常採用として有効化せず、未採用理由を照合ログに記録する
- 回答内の条件式、該当日付・台番一覧、集計表が最初から矛盾している条件は、Webアプリ側で無理に補正して合わせない
- 採用条件のラベル名や期待値表示だけを写して終わらせず、実際にWebアプリのバックテストで再現できる条件式に落とし込む
- 該当日付・台番一覧がある場合は、Webアプリの該当台と1件ずつ突き合わせる
- 順位、次点差、近隣、履歴不足の定義が曖昧な条件は、ラベルだけ実装せず参考条件として扱う
- Webアプリで回答値を再現できない条件は、通常採用条件として残さず、未採用理由を照合ログに記録する
