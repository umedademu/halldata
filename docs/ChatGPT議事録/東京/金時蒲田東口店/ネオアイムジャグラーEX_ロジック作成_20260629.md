## 結論

金時蒲田東口店の **ネオアイムジャグラーEX** は、単純な点数上位・毎日1位狙いでは弱く、**「高稼働で見られていた台が直近急沈みした時」** と、特定日だけ強く出る **「周辺に高内容が出た後の中期沈み・未返済台」** を条件として拾う方が実戦向きでした。

この回答では、指示書どおり分析レポートではなく、後半に **Codexがそのまま実装できる正本** を置きます。指示書上も、最終目的は分析ではなく「実装用の正本」を作ることとされています。

## 2. 高内容日の定義

ネオアイム特例として、成功判定は **設定5・6級** を主指標にしました。指示書でも、ネオアイムは設定5・6級に座ることだけを成功とみなし、設定4以下は今回の目的では失敗扱いとされています。

| 区分   | 定義                         |   |                                          |
| ---- | -------------------------- | - | ---------------------------------------- |
| 準高内容 | `G >= 2500 && (p56 >= 0.30 |   | (rbRate <= 315 && combinedRate <= 145))` |
| 高内容  | `G >= 3000 && p56 >= 0.50` |   |                                          |
| 強高内容 | `G >= 4000 && p56 >= 0.70` |   |                                          |

`p56` は、設定1〜6のBIG・REG確率を使い、各設定の対数尤度を正規化して `設定5推定率 + 設定6推定率` として計算しました。これは指示書のネオアイム設定推定率計算方法に合わせています。

## 7. 実戦での優先順位

まず **特定日** なら、`特定日_自由MAX_周辺高内容中期沈み未返済` を最優先します。これは点数より優先してよい条件です。

逆に、`g7 <= 10000` だけで「冷えている」と見るのは危険です。直近7日G数が少なくても、沈み不足かつ前日RBが枯れていない台はRB 1/388.4まで悪化したため、見送り条件にします。

# 3. ネオアイム設定推定率

設定別確率：
| 設定 | BIG確率 | REG確率 |
|---|---:|---:|
| 1 | 1/273.1 | 1/439.8 |
| 2 | 1/269.7 | 1/399.6 |
| 3 | 1/269.7 | 1/331.0 |
| 4 | 1/259.0 | 1/315.1 |
| 5 | 1/259.0 | 1/255.0 |
| 6 | 1/255.0 | 1/255.0 |

設定推定方法：
- 各台の当日実績 G, BB, RB から設定1〜6の対数尤度を計算する。
- 組み合わせ項は設定間比較では共通なので省略可。
- 各設定sの logWeight:
  BB * log(pB_s) + (G - BB) * log(1 - pB_s)
  + RB * log(pR_s) + (G - RB) * log(1 - pR_s)
- 最大logWeightを引いて exp に戻し、合計1になるよう正規化する。
- p56 = p5 + p6
- p4minus = p1 + p2 + p3 + p4
- G=0の台は推定不能として一様分布、つまり p56=2/6 としてよい。ただし高内容判定には使わない。

# 12. 検証方法・実装完了条件

必ず以下を実施すること。

- Webアプリ上で実際にバックテストを回し、回答内に書いた採用条件ごとの選択台数、総G数、BB確率、RB/REG、合算、平均差枚、機械割と照合する。
- Webアプリ側のバックテスト結果と回答内のバックテスト結果が、実用上許容できる範囲まで一致しない限り、実装完了扱いにしない。
- ここでいう許容範囲は、選択台数、総G数、BB数、RB数などの母数がほぼ一致し、確率、機械割、平均差枚の差が丸め誤差や表示単位差で説明できる程度とする。
- 回答内では整合しているのにWebアプリで一致しない場合は、条件式、最新日除外、未来情報除外、対象機種名、台番、履歴計算、通常日/イベント日の分岐、集計期間の違いを疑い、Webアプリ上で再検証しながら修正する。
- ただし、同じ条件について主要なズレ原因を3つ確認しても一致しない場合、または30分以上かかる場合は、通常採用として有効化せず、未採用理由を照合ログに記録する。
- 回答内の条件式、該当日付・台番一覧、集計表が最初から矛盾している条件は、Webアプリ側で無理に補正して合わせない。
- 採用条件のラベル名や期待値表示だけを写して終わらせず、実際にWebアプリのバックテストで再現できる条件式に落とし込む。
- 該当日付・台番一覧がある場合は、Webアプリの該当台と1件ずつ突き合わせる。
- 順位、次点差、近隣、履歴不足の定義が曖昧な条件は、ラベルだけ実装せず参考条件として扱う。
- Webアプリで回答値を再現できない条件は、通常採用条件として残さず、未採用理由を照合ログに記録する。
- Webアプリ照合では、最初から全条件で設定分布を表示しない。原則OFFで主要成績を合わせ、設定推定率や設定分布が必要な条件だけ最終確認時にONにする。
