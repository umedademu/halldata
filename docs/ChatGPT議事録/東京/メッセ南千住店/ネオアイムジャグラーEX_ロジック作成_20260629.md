# 2. 高内容日の定義

ネオアイムジャグラーEXなので、成功判定は **設定5・6推定率** を最重要にしました。設定列はロジックに使わず、G数・BB・RBから設定1〜6の尤度を再計算しています。

| 区分   | 定義                                                             |
| ---- | -------------------------------------------------------------- |
| 強高内容 | `G >= 4000 && p56 >= 0.70 && rbRate <= 300 && combined <= 145` |
| 高内容  | `G >= 3000 && p56 >= 0.50 && rbRate <= 330 && combined <= 150` |
| 準高内容 | `G >= 2500 && p56 >= 0.30 && rbRate <= 360 && combined <= 155` |

`p56` は、ネオアイムの設定別BIG確率・REG確率を使い、各台の `G, BB, RB` から設定1〜6の対数尤度を計算し、正規化したうえで `設定5推定率 + 設定6推定率` としました。

# 3. 見えたクセ

一番使えるのは、「単純な高スコア」ではなく、**REGや合算が見えない期間があり、かつ過去の高内容や長期空きと重なる台** でした。特に強かったのは次の4系統です。

| クセ                    | 実戦解釈                             |
| --------------------- | -------------------------------- |
| 2日沈み + 高内容から21日以上空き   | しばらく高内容を使っていない台を、短期で沈んだ後に戻す      |
| 7日合算枯れ + 近10日以内に高内容あり | 直近に使った台を完全には切らず、見え方が悪くなったところを再利用 |

| 高内容後3日で大きく不発          | 高内容っぽい履歴がありながら出玉で処遇完了していない台を再利用  |

# ネオアイム設定推定率の計算

ネオアイムジャグラーEXの設定別ボーナス確率：

| 設定 | BIG確率 | REG確率 | 合成確率 |
|---:|---:|---:|---:|
| 1 | 1/273.1 | 1/439.8 | 1/168.48 |
| 2 | 1/269.7 | 1/399.6 | 1/161.02 |
| 3 | 1/269.7 | 1/331.0 | 1/148.61 |
| 4 | 1/259.0 | 1/315.1 | 1/142.15 |
| 5 | 1/259.0 | 1/255.0 | 1/128.49 |
| 6 | 1/255.0 | 1/255.0 | 1/127.50 |

各台の実績について、G数をG、BBをB、RBをRとする。
各設定sについて、pB_s、pR_sを使って以下を計算する。

logWeight_s =
B * log(pB_s) + (G - B) * log(1 - pB_s)
+
R * log(pR_s) + (G - R) * log(1 - pR_s)

全設定のlogWeightの最大値を引いてexpし、合計1になるよう正規化する。
p56 = setting5Prob + setting6Prob
p4down = setting1Prob + setting2Prob + setting3Prob + setting4Prob

設定列とブドウ列は、最終ロジックの説明変数には使わない。

- Webアプリ上で実際にバックテストを回し、回答内に書いた採用条件ごとの選択台数、総G数、BB確率、RB/REG、合算、平均差枚、機械割と照合する
- Webアプリ側のバックテスト結果と回答内のバックテスト結果が、実用上許容できる範囲まで一致しない限り、実装完了扱いにしない
- ここでいう許容範囲は、選択台数、総G数、BB数、RB数などの母数がほぼ一致し、確率、機械割、平均差枚の差が丸め誤差や表示単位差で説明できる程度とする
- 回答内では整合しているのにWebアプリで一致しない場合は、条件式、最新日除外、未来情報除外、対象機種名、台番、履歴計算、通常日/イベント日の分岐、集計期間の違いを疑い、Webアプリ上で再検証しながら修正する
- ただし、同じ条件について主要なズレ原因を3つ確認しても一致しない場合、または30分以上かかる場合は、通常採用として有効化せず、未採用理由を照合ログに記録する
- 回答内の条件式、該当日付・台番一覧、集計表が最初から矛盾している条件は、Webアプリ側で無理に補正して合わせない
- 採用条件のラベル名や期待値表示だけを写して終わらせず、実際にWebアプリのバックテストで再現できる条件式に落とし込む
- 該当日付・台番一覧がある場合は、Webアプリの該当台と1件ずつ突き合わせる
- 順位、次点差、近隣、履歴不足の定義が曖昧な条件は、ラベルだけ実装せず参考条件として扱う
- Webアプリで回答値を再現できない条件は、通常採用条件として残さず、未採用理由を照合ログに記録する
- Webアプリ照合では、最初から全条件で設定分布を表示しない。原則OFFで主要成績を合わせ、設定推定率や設定分布が必要な条件だけ最終確認時にONにする
